# Phase 10 — Локализация CRM (немецкий, английский, русский): план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Запрос пользователя (2026-11-19): «добавить два языка, английский и немецкий, немецкий сделать основным, это именно для CRM; получается три языка — русский, немецкий и английский, немецкий по умолчанию».
Статус документа: **редакция 1, согласована (2026-11-19)**. Решения I1–I10 и глоссарий одобрены сообщением «Согласен, начинай»; роль «Менеджер» — «Mitarbeiter» (предложенный вариант, пользователь возражений не высказал). Реализация — раздел 9 и отчёт в SPEC.

## 1. Цель и границы

Цель: весь интерфейс Modulyn доступен на трёх языках — **немецкий (по умолчанию)**, английский, русский. Каждый человек выбирает свой язык; кто ничего не выбирал — видит немецкий.

Входит: интерфейс CRM компании, общий вход и выбор компании, приглашения и сброс пароля, администрирование платформы; сообщения об ошибках из API, которые видит пользователь; письма (приглашение, сброс пароля); служебные страницы API (переход между поддоменами); форматы дат; тесты; синтетические данные (`db:seed`).

Не входит: перевод данных (имена, сообщения из заявок, названия компаний, подписи полей, которые ввёл администратор); документация проекта (README, docs, SPEC остаются на русском); инструкция подключения сайта для разработчиков (`docs/integrations/web-forms.md` — по запросу, отдельно); другие языки (добавляются потом одним файлом словаря).

## 2. Что есть сейчас (проверено 2026-11-19 по коду)

- Интерфейс: ~280 строк с русским текстом в 20 файлах `apps/web/src`; `<html lang="ru">`; даты через `toLocaleString('ru-RU')`.
- API: ~80 сообщений об ошибках на русском (`BadRequestException('…')` и т.п.), которые интерфейс показывает как есть; HTML-страницы перехода (`handoff`); 2 шаблона писем (`apps/api/src/mail/templates.ts`).
- Язык нигде не хранится; механизма переводов нет.
- Seed: подпись доп. поля точки Nova — «Программа».

## 3. Как будет выглядеть результат

1. Человек открывает `app.<домен>` впервые — страница входа на немецком; в углу переключатель **DE · EN · RU**.
2. После входа язык берётся из его аккаунта (по умолчанию `de`); переключатель в шапке CRM меняет язык сразу и сохраняет его в аккаунте — на всех устройствах и во всех его компаниях.
3. Ошибки из API приходят на языке пользователя («Bitte geben Sie einen Namen ein»).
4. Приглашение сотруднику приходит на языке того, кто приглашает; ссылка открывает страницу приглашения на этом языке (переключатель тоже есть).
5. Даты: `19.11.2026, 14:05` (de), `19/11/2026, 14:05` (en), `19.11.2026, 14:05` (ru).

## 4. Решения для согласования

| ID | Вопрос | Предложение | Альтернативы |
| --- | --- | --- | --- |
| I1 | Языки и язык по умолчанию | `de` (по умолчанию), `en`, `ru` — для всего продукта, включая платформу и письма | Только CRM компании, а платформа и вход на русском — неудобно, два разных механизма |
| I2 | Чей выбор языка | **Личный выбор человека**, хранится в аккаунте (`users.locale`, у администраторов платформы — `platform_admins.locale`), по умолчанию `de`. До входа (страница входа, приглашение, сброс пароля) — язык из cookie браузера, по умолчанию `de`; при входе он не переносится в аккаунт автоматически | Язык компании для всех её сотрудников (администратор выбирает) — проще, но русскоязычный сотрудник немецкой студии не сможет выбрать русский. Можно добавить позже как «язык по умолчанию компании» |
| I3 | Язык браузера (`Accept-Language`) | **Не использовать**: по умолчанию всегда немецкий, как вы сказали; человек переключает сам один раз | Угадывать по браузеру — англоязычный браузер в Германии дал бы английский вместо немецкого |
| I4 | Письма | Приглашение — на языке **пригласившего** (он знает сотрудника); язык сохраняется в приглашении и открывает страницу приглашения на нём же. Сброс пароля — на языке аккаунта. Первому администратору новой компании — на языке администратора платформы | Всегда немецкий; выбор языка письма в форме приглашения — лишнее поле |
| I5 | Сообщения API | API хранит **ключи** сообщений и переводит их сам на язык пользователя (аккаунт → cookie → `de`); в ответе по-прежнему `message` (готовый текст) и, где есть, `code`. Интерфейс не меняет логику показа ошибок | API отдаёт только коды, интерфейс переводит — чище, но переписывать обработку ошибок во всех экранах; для MVP избыточно |
| I6 | Как устроены переводы | Без новых библиотек: общий пакет `packages/i18n` — словари TypeScript (`de.ts` — основной, `en.ts`, `ru.ts`) с одинаковыми ключами и подстановками `{name}`. **Нет перевода в любом языке — ошибка сборки** (проверка типов + unit-тест). Используется и веб-интерфейсом, и API. Адреса страниц без языка (`/leads`, не `/de/leads`) — язык не часть адреса | Библиотека `next-intl` — ещё одна зависимость и своя маршрутизация по языкам; адреса с `/de/…` — ломают уже работающие ссылки и не нужны для CRM за входом |
| I7 | Перевод текстов | Переводы на немецкий и английский делаю я по **глоссарию** (раздел 5); немецкий — с обращением **«Sie»**. Перед использованием с клиентом немецкий текст **просматривает носитель языка** (вы или Nova) — я записываю, что проверено | Профессиональный переводчик сразу — дольше; машинный перевод без глоссария — разнобой терминов |
| I8 | Форматы | Даты и числа — через `Intl` по языку (`de-DE`, `en-GB`, `ru-RU`); часовой пояс — как сейчас, браузера | Фиксировать `Europe/Berlin` — отдельное решение, если появятся сотрудники в других поясах |
| I9 | Существующие данные | Всем существующим аккаунтам — `de`. Seed: подпись доп. поля Nova «Программа» → «Programm» (это данные: у уже созданных точек подпись меняет администратор) | Оставить русский у существующих — непоследовательно с «немецкий по умолчанию» |
| I10 | Проверки | Unit: у трёх словарей одинаковые ключи и подстановки, нет пустых строк. Интеграционные: сообщения API на `de` по умолчанию, на `en`/`ru` после выбора; выбор сохраняется в аккаунте; язык писем; язык недоступен чужим (меняется только свой). Браузер: ключевые экраны на трёх языках на 1280 и 375 px (немецкие слова длиннее — проверка, что ничего не ломается). Smoke: страница входа на немецком | Только ручная проверка — пропущенные переводы найдутся у клиента |

## 6. Изменения схемы

- enum `Locale` (`de`, `en`, `ru`); `users.locale`, `platform_admins.locale` — `NOT NULL DEFAULT 'de'`; `invitations.locale` — `NOT NULL DEFAULT 'de'`.
- Права роли API: `UPDATE (locale)` на `users` и `platform_admins` — только этот столбец. Новых таблиц нет; RLS не меняется (`users` и `platform_admins` — глобальные таблицы, человек меняет только свою строку через API).
- Маршруты: `PUT /api/auth/locale` (свой язык; во всех трёх контекстах; для гостя — только cookie).

## 8. Риски

- **Качество немецкого.** Я пишу грамотно, но тон и термины для клиента лучше подтвердить носителю языка — поэтому I7 и отдельный список строк в отчёте.
- **Длинные немецкие слова** могут ломать кнопки и меню на телефоне — отдельная проверка 375 px (10.6).
- **Сообщения API со склеенным текстом** (`Поддомен «${slug}» уже занят`) переводятся с подстановками — проверка совпадения подстановок во всех языках (I10).
- **Незакоммиченная Phase 9.** Чтобы изменения не смешались, Phase 9 лучше закоммитить до начала Phase 10.
- **Развёртывание.** Языки не мешают развёртыванию и не зависят от него.

## 9. Реализация (P10-001, 2026-11-19)

Сделано по I1–I10; отчёт с фактическими проверками — SPEC, «Отчёт по каждому подшагу Phase 10». Таблица всех фраз для проверки носителем — [docs/i18n/review.md](../docs/i18n/review.md).

Код: пакет `packages/i18n` (языки, перевод, форматы дат, 384 фразы в шести разделах); миграция `20261119100000_phase10_locale` (enum `locale`, `users.locale`, `platform_admins.locale`, `invitations.locale`, по умолчанию `de`); API — `apps/api/src/i18n.ts` (`t()` на языке запроса), язык в контексте запроса (cookie до входа, аккаунт после), `PUT /api/auth/locale`, все сообщения ошибок, служебные страницы и письма через словарь; интерфейс — `apps/web/src/i18n/` (провайдер, переключатель, язык для серверной отрисовки), все экраны через словарь.

Отличия и уточнения относительно разделов 4–6:

- **I6, устройство словаря.** Вместо трёх файлов `de.ts`/`en.ts`/`ru.ts` — разделы, где **каждая фраза сразу на трёх языках** (`{ de, en, ru }`): пропустить язык невозможно (ошибка типов), переводы одной фразы стоят рядом. Гарантии те же, что в I6; проверка подстановок, пустых строк и кириллицы в de/en — unit-тест пакета.
- **Раздел 6, права.** Новых прав не понадобилось: роль API уже могла обновлять `users`, `platform_admins` и `invitations` (Phase 2–5). Меняется только строка своего аккаунта — через `PUT /api/auth/locale`.
- **I5.** У двух ошибок второго фактора появились коды (`MFA_INVALID_CODE`, `MFA_EXPIRED`): интерфейс раньше различал их по русскому тексту.
- **I4.** Повторная отправка приглашения — на языке, сохранённом в приглашении. Служебные страницы перехода между поддоменами открываются без входа, поэтому их язык — из cookie этого браузера.
- **Каталог модулей.** Название модуля в базе («Заявки») не меняется — интерфейс показывает название и описание модуля из словаря по ключу модуля.
- **I9.** Seed: точка Nova — «Website bjjmoenchengladbach.de (lokal)», подпись «Programm». Уже созданные в локальной базе точки сохраняют прежние название и подпись (это данные) — их меняет администратор.
