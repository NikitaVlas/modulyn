# Phase 7 — Leads: план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Модель: [phase2_design.md](phase2_design.md) (Lead, LeadStatusHistory); права: [phase3_design.md](phase3_design.md) (A1, A2); модуль: [phase6_design.md](phase6_design.md).
Статус документа: **редакция 1, согласована (2026-11-17)**. Решения L1–L9 и Phase 7 одобрены сообщением «Согласен, начинай». Реализация — раздел 8 и отчёт в SPEC.

## 1. Цель и границы

Цель: первый рабочий модуль CRM. Сотрудники компании видят заявки, фильтруют и сортируют их, открывают карточку, меняют статус с полной историей; администратор назначает ответственного.

Входит (подшаги SPEC 7.1–7.7): список с фильтрами, сортировкой и постраничным выводом; карточка; смена статуса с историей в одной транзакции; назначение ответственного; ручное создание заявки (L4); интерфейс; тесты прав и изоляции.

Не входит: приём заявок с сайта (Phase 8), удаление заявок и сроки хранения (9.5), комментарии и задачи по заявке, уведомления, импорт/экспорт.

Права — как уже согласовано (A2): **менеджер и администратор компании видят все заявки компании и меняют их статус; назначает ответственного только администратор**. Модуль «Заявки» должен быть включён (Phase 6), иначе `MODULE_DISABLED`.

## 2. Как это будет работать

1. «Заявки» в меню → таблица: имя, контакт, источник (сайт / вручную, какая форма), статус, ответственный, дата. Новые сверху.
2. Фильтры над таблицей: статус (несколько), ответственный (я / без ответственного / конкретный сотрудник), поиск по имени, email или телефону. Фильтры и страница сохраняются в адресе — ссылку можно отправить коллеге.
3. Клик по строке → карточка: все данные заявки, сообщение из формы, история статусов (когда, кто, с какого на какой).
4. В карточке: смена статуса (любая роль), назначение ответственного (только администратор).
5. Кнопка «Новая заявка» — для звонка или визита: имя и хотя бы один контакт (L4).

## 3. Решения для согласования

| ID | Вопрос | Предложение | Альтернативы |
| --- | --- | --- | --- |
| L1 | Переходы статусов | **Любой статус → любой другой** (NEW, IN_PROGRESS, CONTACTED, CONVERTED, CLOSED). Каждая смена — запись в истории. Ошибочный переход исправляется следующим переходом, история хранит оба | Жёсткая схема (NEW → IN_PROGRESS → …) — защищает от ошибок, но мешает небольшой команде |
| L2 | Список | Постранично по 25 (выбор 25/50/100), сортировка по дате создания (новые/старые), фильтр по статусам, ответственному и поиск по имени/email/телефону (без учёта регистра). Номер страницы и фильтры — в адресе страницы | Бесконечная прокрутка — сложнее поделиться ссылкой |
| L3 | Одновременная смена | Запрос смены статуса содержит статус, который видел пользователь. Если заявку уже изменил кто-то другой — 409 «Заявку уже изменили», карточка обновляется. Так ни одна смена не теряется и история не противоречит статусу | «Последний выигрывает» — тихо теряет чужое изменение |
| L4 | Ручное создание заявки | **Да:** имя и хотя бы один контакт (email или телефон), сообщение — необязательно; источник «Вручную»; статус NEW; в истории — кто создал. Создавать могут обе роли | Только заявки с сайта (Phase 8) |
| L5 | Назначение | Только администратор; только **активный** участник этой компании (любой роли); можно снять назначение. Запись в аудит компании. История назначений отдельно не ведётся (в ТЗ — только история статусов) | Отдельная история назначений в карточке |
| L6 | Изменение данных заявки (имя, контакты) | **Не в Phase 7**: заявка — то, что прислал человек. Исправления — отдельной задачей позже, если понадобится | Редактирование обеими ролями |
| L7 | Удаление заявок | Не в Phase 7: удаление персональных данных определяется в 9.5 (GDPR). Для ненужных заявок — статус «Закрыта» | Удаление администратором |
| L8 | Что видно в списке | Имя, email/телефон, источник, статус, ответственный, дата. Текст сообщения — только в карточке | Сообщение в списке — больше персональных данных на экране |
| L9 | Уведомления | Не в Phase 7 (например, письмо менеджеру при назначении — позже) | Письмо при назначении сразу |

## 4. API (план)

Все маршруты — на поддомене компании, `@RequireModule('leads')`, транзакция компании (RLS):

| Метод | Путь | Кто | Что |
| --- | --- | --- | --- |
| GET | `/api/leads?status=NEW,IN_PROGRESS&assignee=me|none|<userId>&q=…&sort=created_desc|created_asc&page=1&pageSize=25` | обе роли | страница списка + общее число |
| GET | `/api/leads/:id` | обе роли | карточка + история статусов (с именами сотрудников) |
| POST | `/api/leads` | обе роли | ручное создание (L4) |
| POST | `/api/leads/:id/status` `{ from, to }` | обе роли | смена статуса + история одной транзакцией (L1, L3) |
| PUT | `/api/leads/:id/assignee` `{ userId \| null }` | TENANT_ADMIN | назначение (L5) |
| GET | `/api/leads/assignees` | обе роли | активные участники для фильтра и выбора ответственного |
| GET | `/api/leads/summary` | обе роли | сводка (Phase 6) |

Заявка другой компании и несуществующая — одинаковый 404 (IDOR). Неверные параметры — 400 с понятным сообщением.

Схема не меняется: Lead и LeadStatusHistory созданы в Phase 2 (составные FK: история и ответственный — только в своей компании). Для поиска по имени/email/телефону при росте данных можно будет добавить индекс; на объёме MVP не нужен.

## 5. Подшаги и проверки

| ID | Что делаем | Проверки |
| --- | --- | --- |
| 7.1 | Согласовать L1–L9 | Явное согласование в SPEC |
| 7.2 | Список и карточка | Фильтры, сортировка, страницы, поиск; только своя компания; чужой id — 404 |
| 7.3 | Смена статуса и история одной транзакцией | Статус и запись истории всегда вместе; устаревший `from` — 409, ничего не меняется; параллельные смены — одна проходит |
| 7.4 | Назначение ответственного | Только администратор (менеджер — 403); неактивный и чужой участник — отказ; снятие назначения; аудит |
| 7.5 | Таблица и фильтры в интерфейсе | Загрузка, пустое состояние, ошибки, сортировка, фильтры в адресе, вид на телефоне |
| 7.6 | Карточка, действия, история; ручное создание | Результат действия виден сразу; понятный отказ при недостатке прав и при конфликте |
| 7.7 | Модуль целиком | IDOR, обе роли, назначенные и неназначенные заявки, статусы и история, отключённый модуль, все тесты Phase 1–6 |

## 6. Критерии готовности Phase 7

1. Решения L1–L9 согласованы и записаны в SPEC.
2. Сотрудники работают со списком, карточкой и статусами; администратор назначает ответственных.
3. Статус и история всегда согласованы; одновременные изменения не теряются молча.
4. Заявки другой компании недоступны ни через список, ни по id; отключённый модуль закрыт.
5. `pnpm check`, `pnpm test:integration`, `pnpm smoke` проходят; сценарий проверен в браузере, включая ширину телефона; результаты в SPEC.

## 7. Риски

- **Поиск по персональным данным** — только внутри своей компании (RLS) и только для вошедших сотрудников; поисковый запрос не пишется в логи.
- **Рост числа заявок** — постраничный вывод и индексы `(tenant_id, status, created_at)` уже есть; поиск без индекса станет медленным на десятках тысяч заявок — тогда добавим индекс.

## 8. Реализация (P7-001, 2026-11-17)

Отличия от плана и решения внутри одобренной фазы:

- **Хранилище** `apps/api/src/database/leads-store.service.ts`: смена статуса — условный `UPDATE … WHERE status = from RETURNING` и запись истории в одной транзакции компании; при несовпадении — `409 LEAD_CHANGED` с текущим статусом (L3). Назначение — `updateManyAndReturn` с `assignedToId` (не `disconnect`), проверка активного участия, аудит `lead.assigned/unassigned` (в метаданных только id сотрудника).
- **Разбор фильтров** вынесен в `parseFilters` (контроллер) с unit-тестами. Повторённый параметр адреса (`?status=A&status=B`) отклоняется 400 — тест нашёл, что сначала он молча игнорировался; несколько статусов передаются через запятую.
- **Поиск** — `contains` без учёта регистра (Prisma `mode: 'insensitive'`, PostgreSQL ILIKE), работает и для кириллицы.
- **Интерфейс:** состояние списка в адресе (`/leads?status=…&assignee=…&q=…&sort=…&page=…`); на узких экранах карточки вместо таблицы; статус одной заявки — в единственном числе («Новая», «Клиент»), в фильтрах и сводке — во множественном.
- **Схема не менялась.**
