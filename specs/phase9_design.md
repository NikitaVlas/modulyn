# Phase 9 — Integration Testing & MVP Finalization: план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Предыдущие фазы: [phase2](phase2_design.md) (модель, удаления — 9.5), [phase3](phase3_design.md) (вход, сессии), [phase4](phase4_design.md) (компании), [phase5](phase5_design.md) (сотрудники), [phase7](phase7_design.md) (заявки, L7 — удаление в 9.5), [phase8](phase8_design.md) (приём с сайтов, W7 — очистка журнала в 9.5).
Статус документа: **редакция 1, согласована (2026-11-17)**. Решения F1–F10 и Phase 9 одобрены сообщением «Согласен, начинай». Реализация — раздел 9 и отчёт в SPEC.

## 1. Цель и границы

Цель: убедиться, что всё сделанное в Phase 1–8 работает **вместе**, закрыть то, что откладывалось «до 9.5» (хранение и удаление данных), научиться восстанавливать базу из резервной копии и передать MVP на приёмку с честным списком ограничений и отдельным планом выхода в интернет.

Входит (подшаги SPEC 9.1–9.7): сквозные сценарии; проверка границ безопасности по всем маршрутам; проверка интерфейса и ошибок; резервное копирование и восстановление; сроки хранения, очистка технических данных и удаление заявки; итоговая документация; отчёт для приёмки и план развёртывания.

Не входит: само развёртывание в интернете, DNS, TLS, выбор хостинга и почтового сервиса (только план — F9); подключение живого сайта Nova (после развёртывания, W10); новые функции (редактирование заявок, уведомления, капча, удаление аккаунтов и компаний через интерфейс).

## 2. Что есть сейчас (проверено 2026-11-17 по коду)

- **Тесты:** 47 unit и 105 интеграционных (по фазам: изоляция, вход, платформа, сотрудники, модули, заявки, приём форм), smoke. Каждая фаза проверена отдельно; **сквозного сценария через все фазы нет**. Браузерные проверки делались вручную; инструментов браузерных автотестов в проекте нет.
- **Защита маршрутов:** глобальный `AuthGuard` с декораторами `@Contexts/@Public/@Roles/@RequireModule`. Проверяется тестами каждой фазы, но **нет общей проверки «каждый маршрут защищён»** — новый маршрут без декоратора заметят только по ревью.
- **Резервные копии:** нет ни команды, ни инструкции. Данные — в named volume PostgreSQL.
- **Накопление данных:** просроченные коды перехода и ссылки сброса пароля удаляются попутно; **сессии (`user_sessions`, `tenant_sessions`, `platform_sessions`), приглашения, счётчики `auth_throttle`, журнал приёма `form_submissions` и журналы аудита не очищаются никогда.** Удаления заявок нет (L7), удаления компаний и аккаунтов нет (B5, phase5).
- **Ключи вне БД:** `PLATFORM_TOTP_KEY`, ключи подписи JWT и прочее в `.env`. Без `PLATFORM_TOTP_KEY` резервная копия БД не восстановит второй фактор администраторов платформы.

## 3. Как будет выглядеть результат

1. Один автотест проходит весь путь: платформа создаёт компанию → первый администратор принимает приглашение из письма → приглашает менеджера → платформа включает модуль → администратор создаёт точку приёма → «сайт» присылает заявку → менеджер берёт её в работу → администратор назначает → закрывает. Плюс тот же путь вручную в браузере по чек-листу.
2. Автотест перебирает **все** маршруты API и для каждого проверяет: без входа, с чужим контекстом, с ролью ниже нужной, при отключённом модуле — отказ.
3. `pnpm db:backup` делает файл копии; `pnpm db:restore-check` восстанавливает его в отдельную базу и сверяет.
4. Устаревшие технические записи удаляются сами; администратор компании может удалить заявку по запросу человека.
5. Документы: запуск с нуля, эксплуатация (копии, восстановление, ключи, диагностика), план развёртывания, отчёт приёмки с чек-листом, который вы проходите сами.

| --- | --- | --- | --- |
| F1 | Сквозные сценарии (9.1) | **Автотест на уровне HTTP** (как существующие интеграционные, `node:test` + письма из памяти) через все фазы — раздел 3, п. 1; плюс **ручной прогон в браузере** по чек-листу, результат — в отчёте. Синтетические данные, отдельная тестовая база | Браузерные автотесты (Playwright): сильнее для интерфейса, но новая тяжёлая зависимость, загрузка браузеров, медленный и хрупкий набор для MVP |

(б) Проверка заголовков безопасности, cookies, CSRF, лимитов. (в) `pnpm audit` зависимостей — найденное исправляем или фиксируем. (г) Обзор кода по чек-листу OWASP ASVS (уровень 1) с записью результата | Только ручной обзор — без защиты от будущих ошибок; внешний пентест — после развёртывания, отдельно |
| F3 | Интерфейс и сбои (9.3) | Размеры экрана: **375 px (телефон) и 1280 px**. Ожидание: понятное сообщение, без белого экрана и потери введённого текста там, где это возможно. Мелкие найденные недочёты исправляем в Phase 9 | Добавить 768 px (планшет) — дольше, пользы мало |

| F5 | Сроки хранения (9.5) | **Автоочистка технических данных:** сессии — через 30 дней после окончания или отзыва; приглашения — через 30 дней после истечения/принятия/отзыва; коды перехода, ссылки сброса, счётчики лимитов — через 1 день после истечения; журнал приёма заявок — **90 дней** (W7); журналы аудита компании и платформы — **1 год**. **Заявки и их история автоматически не удаляются** — компания хранит их, пока нужны, удаляет по запросу (F6). Сроки — разумное предложение для MVP, а не юридическое заключение: окончательно их подтверждает владелец данных (компания) | Аудит хранить 2–3 года; заявки удалять автоматически через N лет — сейчас не нужно |

Ручной запуск — `pnpm db:cleanup` | Отдельный cron-контейнер — ещё один сервис; давать приложению DELETE на журналы — шире права, чем нужно |

## 5. Изменения схемы и кода

- Миграция: функция `modulyn_cleanup()` (`SECURITY DEFINER`, владелец `modulyn_owner`, фиксированный `search_path`), `GRANT EXECUTE` роли приложения. Индексы по датам для очищаемых таблиц, где их нет.
- Удаление заявки (F6): `GRANT DELETE ON lead_status_history`, `GRANT UPDATE (lead_id) ON form_submissions` роли приложения; всё в транзакции компании под RLS. На `leads` право DELETE уже есть с Phase 2.
- Новых таблиц нет. Контракты: ответ удаления заявки. Web: кнопка в карточке заявки.
- Скрипты: `db:backup`, `db:restore-check`, `db:cleanup`; папка `backups/` — в `.gitignore` и `.dockerignore`.

## 7. Критерии готовности Phase 9

- `pnpm check`, `pnpm test:integration`, `pnpm smoke`, `pnpm db:drift` — без ошибок; сквозной тест и матрица маршрутов проходят.
- Восстановление из копии проверено командой, а не на словах.
- Технические данные не копятся бесконечно; заявку можно удалить по запросу.
- Документация позволяет запустить проект с нуля и понять, что делать при сбое.
- Отчёт приёмки честно перечисляет ограничения; ничего не опубликовано в интернете.

## 8. Риски

- **Матрица маршрутов найдёт пробел** в уже принятых фазах — исправление может затронуть закоммиченный код; это и есть цель проверки. О каждом таком исправлении — отдельная запись в отчёте.
- **Сроки хранения — юридический вопрос.** F5 — предложение для MVP; для реальных данных Nova срок хранения заявок и аудита подтверждает компания (возможно, с юристом). Изменить сроки — одна миграция.
- **Удаление необратимо.** Ошибочно удалённую заявку вернёт только резервная копия; поэтому F6 — только администратор и с подтверждением.
- **Копия без ключей бесполезна частично:** без `PLATFORM_TOTP_KEY` администраторам платформы придётся заново настроить второй фактор; без ключей сессий — всем войти заново (данные при этом целы). Это отдельно в `docs/operations.md`.
- **Согласие посетителя (phase8, раздел 8):** факт согласия с сайта Nova в CRM не передаётся. Если он должен храниться в CRM — это изменение формы сайта; решение вместе с F5/F6, по умолчанию не делаем.
- **Вход через настоящий Google** не проверен (нужен OAuth-клиент); остаётся в ограничениях, проверяется при развёртывании.

Отличия и уточнения относительно разделов 4–5:

- **F6 / раздел 5.** Вместо права `DELETE` на историю статусов — каскадное удаление по внешнему ключу (`onDelete: Cascade` в схеме): история по-прежнему неизменна для приложения и исчезает только вместе с заявкой. Обнаружено существующим тестом неизменности истории. Ссылка в журнале приёма обнуляется правом `UPDATE` только на столбец `lead_id` (составной ключ не позволяет `SET NULL` одним столбцом).
- **F7.** Таблицы с FORCE RLS функция очищает по одной компании за раз (устанавливая контекст компании), как и приложение; сессии входа, на которые ещё ссылаются живые сессии компаний, не удаляются.
- **F2.** Найден и исправлен пробел: страницы Next.js не запрещали встраивание в чужие сайты (clickjacking) — добавлены заголовки и проверка в smoke. Полная CSP для скриптов — после MVP.
- **F3.** Исправлены сообщения: сеанс завершён (401 после неудачного обновления), сервис недоступен (5xx/502 от прокси), нет связи (сетевая ошибка — раньше необработанный `TypeError`), модуль отключён (403 `MODULE_DISABLED`). Найдено, не исправлено (меняет вход, F8): после повторного входа пользователь попадает на главную компании, а не на исходную страницу — в списке «после MVP».
- **Тестовый помощник `browser.mjs`** теперь всегда указывает длину тела запроса: Node не делает этого для `DELETE`, и сервер принимал тело за второй запрос (400) — ошибка теста, не API.
