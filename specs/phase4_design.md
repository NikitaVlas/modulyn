# Phase 4 — Platform Administration: план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Модель данных: [phase2_design.md](phase2_design.md); вход и сессии: [phase3_design.md](phase3_design.md).
Статус документа: **редакция 3, согласована (2026-11-16)**. Решения B1–B10 и Phase 4 одобрены сообщением «Согласен, начинай». Реализация — раздел 9 и отчёт в SPEC.
История: редакция 2 добавляла роль SUPER_ADMIN (B11–B13, подшаг 4.6) по указанию пользователя; в редакции 3 она убрана по его же решению «я передумал, убрать надо суп админа. Оставить только админа». B11–B13 и 4.6 отменены.

## 1. Цель и границы

Цель: администратор платформы на `admin.<домен>` создаёт компании вместе с их первым администратором, меняет настройки компаний, отключает и включает их, а в Phase 6 — включает им модули. Данных клиентов (лиды, участники) он не видит. Вход на платформу защищён вторым фактором.

Входит в Phase 4 (подшаги 4.1–4.5 SPEC):

- Команда создания первого администратора платформы на сервере (4.1); второй фактор TOTP для всех администраторов платформы (A11).
- Список компаний, создание компании вместе с её первым администратором (4.2).
- Изменение названий, отключение и включение компании с немедленным отзывом сессий; аудит действий платформы (4.3).
- Интерфейс на `admin.<домен>` (4.4).
- Тесты границ: пользователь компании не управляет платформой, администратор платформы не видит лиды и участников компаний (4.5).

Не входит: включение модулей для компании (Phase 6); приглашения по email, управление участниками, сброс пароля по email (Phase 5); логотип и оформление компании (позже); управление администраторами платформы через интерфейс (B9); production DNS/TLS.

## 2. Как это будет работать

1. На сервере владелец выполняет `pnpm platform:create-admin --email ... --name ...`. Команда создаёт администратора и один раз печатает временный пароль.
2. Вход на `admin.<домен>` временным паролем → обязательная смена пароля → обязательная настройка второго фактора: QR-код для приложения-аутентификатора (Google Authenticator, Microsoft Authenticator, 1Password и т.п.) и 10 одноразовых кодов восстановления. Дальше каждый вход — пароль + 6-значный код.
3. Создание компании: название, отображаемое имя («Nova CRM»), поддомен (`nova`), email и имя первого администратора компании. Если человек с таким email уже есть в системе — ему добавляется участие; если нет — создаётся аккаунт и один раз показывается временный пароль, который администратор платформы передаёт ему сам. Первый вход с временным паролем требует смены пароля.
4. Отключение компании: поддомен сразу отвечает 404, все сессии компании отзываются, данные сохраняются. Включение возвращает доступ (пользователи входят заново).
5. Кто что делает дальше: администратор платформы создаёт компанию и её **первого** администратора; сотрудников компании приглашает уже администратор компании (Phase 5); модули компании включает администратор платформы (Phase 6).

## 3. Решения для согласования

| ID | Вопрос | Предложение | Альтернативы |
| --- | --- | --- | --- |
| B1 | Создание первого администратора платформы (4.1) | Команда на сервере `pnpm platform:create-admin --email --name`, работает под ролью владельца схемы (у API нет права создавать администраторов). Генерирует случайный временный пароль (20 символов), печатает его один раз, в БД — только хеш; при первом входе обязательна смена пароля. Публичной регистрации и встроенного пароля нет. Той же командой создаются последующие администраторы | Пароль вводится в команде скрытым вводом — без «временного» шага, но пароль проходит через историю терминала/скрипты |
| B2 | Второй фактор для платформы (A11) | **Обязательный TOTP (RFC 6238) для всех администраторов платформы, уже в Phase 4.** Настройка при первом входе; секрет хранится зашифрованным (AES-256-GCM, ключ `PLATFORM_TOTP_KEY` в `.env`); 10 одноразовых кодов восстановления (в БД — хеши). Повтор одного кода в течение его 30-секундного окна запрещён. Ограничение попыток — как для пароля (A9) | Отложить 2FA до Phase 9 — проще сейчас, но аккаунт с полным контролем над компаниями защищён только паролем |
| B3 | Первый администратор компании | **Создаётся вместе с компанией** (email + имя). Существующий аккаунт — добавляется участие TENANT_ADMIN; новый — аккаунт с временным паролем, показанным один раз администратору платформы, и обязательной сменой при первом входе. Альтернативно человек может войти через Google, если его Google-email совпадает. В Phase 5 к этому добавятся приглашения по email | Компания без администратора до Phase 5 — тогда войти в неё до Phase 5 никто не сможет |
| B4 | Что можно менять в компании | Название (`name`), отображаемое имя (`displayName`), статус. **Поддомен (slug) после создания не меняется**: на нём ссылки, сессии и, в Phase 8, адреса приёма заявок | Разрешить смену slug — нужен отдельный механизм перенаправлений |
| B5 | Отключение компании | Статус SUSPENDED: поддомен сразу 404 (как сейчас), все сессии компании отзываются, коды перехода в неё отклоняются, данные не удаляются. Включение — статус ACTIVE, пользователи входят заново. Физическое удаление компании — не в MVP (сроки хранения — 9.5) | Удаление компании — необратимо, требует решений GDPR |
| B6 | Что администратор платформы видит о компании | Название, поддомен, статус, даты создания и изменения, **число** активных участников. Не видит: лиды, имена и email участников (кроме первого администратора в момент создания), историю, аудит компании | Список участников с email — удобнее для поддержки, но это персональные данные клиентов |
| B7 | Аудит платформы | Запись в `platform_audit_logs` при: создании администратора платформы, входе и неудачной проверке второго фактора, создании компании, изменении настроек, отключении и включении. В записи — кто, что, какая компания, какие поля изменились (без значений персональных данных, без паролей) | Без аудита входов — меньше записей, но не видно попыток подбора |
| B8 | Временные пароли | Общее правило для B1 и B3: 20 случайных символов, показываются один раз, в БД только хеш; флаг «требуется смена пароля» — до смены доступны только `/me`, `/password`, `/logout` (на любом хосте). Срок действия временного пароля — 7 дней, после — нужен новый (повторный выпуск — B9 для платформы, Phase 5 для компаний) | Без срока — забытый временный пароль работает бесконечно |
| B9 | Управление администраторами платформы | Только командой на сервере (создать, заблокировать, выпустить новый временный пароль, сбросить второй фактор). Интерфейса нет | Раздел «Администраторы» в интерфейсе — больше кода и рисков, для одного-двух администраторов не нужно |
| B10 | Где хранится второй фактор | Новые поля в `platform_admins`: `totp_secret_enc`, `totp_enabled_at`, `totp_last_step`, таблица `platform_recovery_codes`; флаг `password_change_required` + `temp_password_expires_at` в `users` и `platform_admins`. Вход в два этапа: после пароля выдаётся короткоживущий (5 мин) промежуточный токен «пароль проверен», полная сессия — только после кода | Второй фактор в отдельной таблице — гибче для будущих WebAuthn-ключей, но сейчас лишнее |

## 4. Изменения схемы и прав (план миграции Phase 4)

```prisma
model User {
  // ... существующие поля
  passwordChangeRequired Boolean   @default(false) @map("password_change_required")
  tempPasswordExpiresAt  DateTime? @map("temp_password_expires_at") @db.Timestamptz(3)
}

model PlatformAdmin {
  // ... существующие поля
  passwordChangeRequired Boolean   @default(false) @map("password_change_required")
  tempPasswordExpiresAt  DateTime? @map("temp_password_expires_at") @db.Timestamptz(3)
  totpSecretEnc          String?   @map("totp_secret_enc")          // AES-256-GCM, base64
  totpEnabledAt          DateTime? @map("totp_enabled_at") @db.Timestamptz(3)
  totpLastStep           BigInt?   @map("totp_last_step")           // защита от повторного использования кода
  recoveryCodes          PlatformRecoveryCode[]
}


model PlatformRecoveryCode {
  id        String    @id @default(uuid(7)) @db.Uuid
  adminId   String    @map("admin_id") @db.Uuid
  codeHash  String    @map("code_hash") @db.VarChar(128)
  usedAt    DateTime? @map("used_at") @db.Timestamptz(3)
  createdAt DateTime  @default(now()) @map("created_at") @db.Timestamptz(3)
  admin     PlatformAdmin @relation(fields: [adminId], references: [id], onDelete: Restrict)
  @@index([adminId])
  @@map("platform_recovery_codes")
}
```

Права `modulyn_app`: `tenants` — добавить INSERT и UPDATE (только столбцы `name`, `display_name`, `status`, `updated_at` — slug неизменяем на уровне прав); `platform_audit_logs` — SELECT, INSERT; `platform_recovery_codes` — SELECT, INSERT, UPDATE; `platform_admins` — UPDATE и новых столбцов. INSERT в `platform_admins` у runtime-роли **нет** — администраторов создаёт только команда B1.

Операции платформы с таблицами компаний (первое участие, отзыв сессий компании) выполняются через `runInTenant` в контексте целевой компании — как и запланировано в Phase 2.

## 5. Устройство кода (план)

```text
apps/api/scripts/platform-admin.mjs     B1/B9: create | block | reset-password | reset-2fa (роль владельца схемы)
apps/api/src/auth/totp.ts               RFC 6238 на node:crypto (HMAC-SHA1, 30 с, 6 цифр, окно ±1 шаг), без новой зависимости
apps/api/src/auth/secret-box.ts         AES-256-GCM для секрета TOTP
apps/api/src/auth/...                   вход платформы в два этапа, обязательная смена пароля (guard), настройка TOTP
apps/api/src/platform/
  tenants.controller.ts                 GET/POST /api/platform/tenants, GET/PATCH /api/platform/tenants/:id  (@Contexts('platform'))
  tenants.service.ts                    валидация, создание компании + первого администратора, жизненный цикл, аудит
apps/api/src/database/platform-store.service.ts   tenants, platform_audit_logs, счётчики участников (только числа)
apps/web/src/features/platform/         список, создание, карточка компании, подтверждение отключения, экран временного пароля
apps/web/src/features/auth/             шаг второго фактора, настройка TOTP с QR-кодом, принудительная смена пароля
```

QR-код рисуется на клиенте из `otpauth://` URI; для этого нужна небольшая библиотека генерации QR в web (версия проверяется при установке). Секрет TOTP показывается один раз и при отображении не уходит на сторонние сервисы.

## 6. Подшаги и проверки

| ID | Что делаем | Проверки |
| --- | --- | --- |
| 4.1 | Команда создания администратора; временные пароли и обязательная смена; TOTP: настройка, вход в два этапа, коды восстановления | Команда отказывает без роли владельца и при существующем email; временный пароль работает один раз до смены и не дольше 7 дней; до смены пароля и настройки TOTP закрыты все маршруты, кроме разрешённых; неверный, просроченный и повторный TOTP-код отклоняются; код восстановления одноразовый; секрет TOTP в БД не хранится открыто; ограничение попыток второго фактора |
| 4.2 | Список и создание компаний с первым администратором | Slug: формат, зарезервированные имена, уникальность (понятная ошибка, не 500); новый и существующий email первого администратора; временный пароль показан один раз; всё в одной транзакции — при ошибке не остаётся компании без администратора |
| 4.3 | Изменение настроек, отключение и включение, аудит | Slug изменить нельзя (в том числе прямым SQL под runtime-ролью); отключение сразу даёт 404 на поддомене и 401 для существующих сессий и кодов перехода; включение возвращает доступ; каждая операция в аудите без персональных данных |
| 4.4 | Интерфейс администратора | Список, создание, карточка, отключение с подтверждением, понятные ошибки; проверка в браузере |
| 4.5 | Границы платформы | Пользователь компании (любая роль) получает 401/404 на маршрутах платформы; токен платформы не работает в компаниях (уже есть в 3.5); ответы платформы не содержат лидов, имён и email участников; все тесты Phase 1–3 проходят |

## 7. Критерии готовности Phase 4

1. Решения B1–B10 согласованы и записаны в SPEC.
2. Первый администратор платформы создаётся только командой на сервере; вход — пароль и второй фактор.
3. Компания создаётся вместе с первым администратором, который может войти; ошибки ввода понятны.
4. Отключение компании закрывает доступ сразу, включение возвращает; данные сохраняются; всё в аудите.
5. Администратор платформы не получает данных клиентов; пользователь компании не управляет платформой.
6. `pnpm check`, `pnpm test:integration`, `pnpm smoke` проходят, сценарий проверен в браузере; результаты записаны в SPEC.

## 8. Риски

- **Потеря второго фактора.** Коды восстановления + команда `reset-2fa` на сервере (B9). Без доступа к серверу и без кодов — восстановление невозможно, это осознанное следствие.
- **Ключ шифрования TOTP.** Потеря `PLATFORM_TOTP_KEY` = всем администраторам платформы нужно заново настроить второй фактор (через команду). Ключ не хранится в БД и не попадает в Git.
- **Временный пароль передаётся вручную** (B3) до появления приглашений по email в Phase 5. Риск перехвата при передаче; смягчение — обязательная смена при первом входе и срок 7 дней.
- **Платформа меняет таблицы компаний.** Только через `runInTenant` для конкретной компании и только для перечисленных операций; отдельный store платформы не имеет методов чтения лидов и участников (проверяется тестом и ESLint-правилом).

## 9. Реализация (P4-001, 2026-11-16)

Отличия от плана и решения внутри одобренной фазы:

- **Ограниченные сессии вместо отдельного «промежуточного» входа для первой настройки.** Администратор без настроенного второго фактора (и пользователь с временным паролем) получает обычную сессию с признаком ограничения; guard пропускает только маршруты с `@AllowRestricted` (`/me`, `/password`, `/logout`, `/logout-all`, `/mfa/setup`, `/mfa/enable`), остальные — 403 с кодом `PASSWORD_CHANGE_REQUIRED` или `MFA_SETUP_REQUIRED`. Признак берётся из БД на каждом запросе, поэтому снимается сразу после смены пароля или включения второго фактора. Для уже настроенного второго фактора — как в B10: после пароля только подписанная cookie `mdl_mfa` на 5 минут, сессия — после кода.
- **TOTP без новой зависимости** (`apps/api/src/auth/totp.ts`, node:crypto); проверено эталонными значениями RFC 6238. Защита от повтора — условный UPDATE `totp_last_step` (атомарно и при параллельных запросах).
- **QR-код** — `qrcode-generator` 2.0.4 (без зависимостей) в web, рисуется в браузере в SVG; `qrcode` отклонён: тянет CLI-зависимости.
- **Права runtime-роли на уровне столбцов:** `tenants` — UPDATE только `name`, `display_name`, `status`, `updated_at` (slug неизменяем даже прямым SQL); `platform_admins` — UPDATE только пароля и полей второго фактора (email, имя, блокировка, создание — только команда). Тест Phase 2 «runtime-роль не меняет tenants» заменён на «не меняет поддомен и не удаляет компании» — изменение статуса и названий теперь разрешено по B4/B5.
- **Команда** `pnpm platform:admin <create|reset-password|reset-2fa|block|unblock> --email … [--name …]` (локально собирает API и запускает `apps/api/scripts/platform-admin.mjs` под владельцем схемы); в Docker — `docker compose run --rm migrate node apps/api/scripts/platform-admin.mjs …`.
- **Число участников** в списке компаний считается запросом в контексте каждой компании (memberships под RLS) — для MVP-объёма компаний достаточно.
- **Синтетический администратор платформы из seed** не имеет второго фактора: при входе локально он проходит обязательную настройку, как настоящий.
- **ESLint-правило для platform-store не добавлено**: в нём нет методов чтения лидов и участников, а тест 4.5 проверяет состав ответов.
