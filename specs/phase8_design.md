# Phase 8 — Web Form Integration: план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Модель: [phase2_design.md](phase2_design.md) (FormEndpoint, FormSubmission, D6, D11); заявки: [phase7_design.md](phase7_design.md).
Статус документа: **редакция 1, согласована (2026-11-17)**. Решения W1–W10 и Phase 8 одобрены сообщением «Согласен, начинай». Реализация — раздел 9 и отчёт в SPEC.

## 1. Цель и границы

Цель: заявка, отправленная с сайта компании, сама появляется в CRM как новая заявка (`WEB_FORM`, статус NEW). Механизм один для всех компаний и не зависит от того, на чём сделан и где размещён сайт (D11): подключение сайта — настройка точки приёма в CRM и несколько строк кода на стороне сайта по инструкции.

Входит (подшаги SPEC 8.8–8.13): универсальный HTTP-контракт приёма; точки приёма компании (режимы SERVER и BROWSER, ключи, секреты, разрешённые адреса сайта, сопоставление полей); приём с защитой от дублей и спама; журнал приёма без содержимого форм; раздел настройки в CRM; инструкция подключения любого сайта с готовыми примерами; тесты.

Не входит: чтение почты по IMAP (отменено, D6); уведомления сотрудникам о новой заявке; капча (подключаемая позже, W2); production-развёртывание CRM (см. W10).

## 2. Что выяснено о сайте первого клиента (8.8)

Проверено 2026-11-17 чтением публичного сайта bjjmoenchengladbach.de (без отправки форм):

- Сайт — одностраничное приложение на React (сборка Vite).
- Форма есть одна — «Пробная тренировка» (`/trial`). Поля: `firstName`, `lastName`, `email`, `phone`, `program` (Erwachsene, Kinder 4–6, Kinder 7–10, Jugendliche), `message` (необязательно), обязательная галочка согласия (без имени поля — в отправку не попадает).
- Браузер отправляет форму JSON-запросом `POST /api/trial` **на сервер самого сайта**; сервер отвечает `{ ok: true }`. Отправку письма, судя по всему, делает этот серверный обработчик.
- На странице «Контакты» формы нет — только телефон и email.

Вывод: у сайта Nova есть собственная серверная часть, поэтому подходит **режим SERVER**.

Дополнительно изучены исходники сайта (папка `Nova-MG`, только чтение, 2026-11-17): `api/trial.php`, `api/trial-crm.php`, `docs/development/trial-crm.md`, `api/config.example.php`.

- Обработчик `/api/trial` — PHP на Strato. Он проверяет поля (обязательны имя, фамилия, email, телефон и программа из четырёх значений), отправляет два письма через SMTP и только после их успеха передаёт заявку в CRM.
- **Клиент CRM на сайте уже написан** (`nova_sync_trial_lead`): один `POST` JSON на адрес из настройки `CRM_INGEST_URL` с заголовком `X-CRM-Integration-Key: <секрет из CRM_INGESTION_SECRET>`; тело — ровно `submissionId` (32 hex-символа, случайный на каждую отправку), `firstName`, `lastName`, `email`, `phone`, `program`, `message`. Успех — любой ответ 2xx. Одна попытка, без повторов, таймаут до 5 секунд, только HTTPS без переадресаций; ошибки CRM не влияют на ответ посетителю и письма. Пустые настройки — синхронизация выключена.
- Значит, **если CRM принимает этот заголовок и эти поля, сайт Nova подключается без изменения кода** — только заполнением `CRM_INGEST_URL` и `CRM_INGESTION_SECRET` в серверном `api/config.php` на Strato (W10).

## 3. Как это будет работать

1. Администратор Nova в CRM → «Настройки» → «Приём заявок» → «Новая точка приёма»: название («Сайт bjjmoenchengladbach.de»), режим SERVER, тип заявки («trial»). CRM один раз показывает адрес и секрет.
2. На сервере сайта Nova в `api/config.php` заполняются `CRM_INGEST_URL = https://nova.modulyn.app/api/webhooks/forms/<ключ>` и `CRM_INGESTION_SECRET = <секрет>` — код сайта уже умеет отправлять заявку (раздел 2). Другие сайты добавляют такой вызов по инструкции. Если CRM недоступна — сайт всё равно отвечает посетителю успехом, письмо уходит как раньше.
3. CRM проверяет ключ и секрет, сопоставляет поля, проверяет данные и в одной транзакции создаёт заявку и запись истории. Повтор той же отправки не создаёт вторую заявку.
4. Сотрудники видят заявку в списке: источник «Сайт · trial», «Программа: Erwachsene» — в тексте сообщения.
5. В «Приём заявок» администратор видит журнал: когда пришло, принято / дубль / отклонено и почему — без содержимого формы.

## 4. Решения для согласования

| ID | Вопрос | Предложение | Альтернативы |
| --- | --- | --- | --- |
| W1 | Контракт приёма | `POST https://<компания>.<домен>/api/webhooks/forms/<publicKey>`, тело JSON до 32 КБ. Ответ `202 { ok: true }` или `{ ok: true, duplicate: true }` — без данных заявки. Ошибки: `400` (поле и причина), `401` (секрет), `404` (неизвестная или отключённая точка, отключённый модуль «Заявки», отключённая компания — одинаково), `413`, `429` | Отдельный домен для приёма — ещё одна запись DNS и сертификат |
| W2 | Режимы | **SERVER** — секрет в заголовке `Authorization: Bearer <секрет>` **или** `X-CRM-Integration-Key: <секрет>` (так уже отправляет сайт Nova), показывается один раз, в БД хеш, можно перевыпустить. **BROWSER** — для сайтов без серверной части: публичный ключ, список разрешённых адресов сайта (Origin), CORS только для них, скрытое поле-ловушка для ботов, лимит частоты. Капча — позже, если спам появится | Только SERVER — не подойдёт статическим сайтам других компаний |
| W3 | Защита от дублей | Ключ повтора: заголовок `Idempotency-Key` или поле `submissionId`, если сайт их передаёт (Nova передаёт `submissionId`); иначе — хеш содержимого формы за 24 часа. Повтор — ответ `duplicate: true`, новая заявка не создаётся, в журнале «Дубль» | Без защиты — двойной клик или повтор отправки создают две заявки |
| W4 | Сопоставление полей | Стандартные имена понимаются сразу: `name` или `firstName` + `lastName`, `email`, `phone`, `message`. Для точки задаётся: тип заявки (`sourceDetail`, например `trial`), переименования полей и список **дополнительных полей**, которые добавляются в сообщение строками «Название: значение» (для Nova — `program` → «Программа»). Неизвестные поля игнорируются | Хранить все поля формы отдельно — нужна новая таблица и экран |
| W5 | Проверка данных | Обязательно имя и хотя бы один контакт (email или телефон); те же ограничения длины, что и у ручной заявки (L4); пустые строки и пробелы отбрасываются | Принимать всё — мусор в CRM |
| W6 | Кто настраивает | **Администратор компании** в CRM: создаёт точки, видит секрет один раз, перевыпускает секрет, отключает точку, смотрит журнал. Менеджер не видит. Платформа не нужна | Только администратор платформы — каждое подключение через вас |
| W7 | Журнал приёма | Хранится: время, точка, результат (принята / дубль / отклонена), код причины, ссылка на заявку. **Содержимое формы не хранится и не пишется в логи** — только в саму заявку. Журнал за последние 90 дней (очистка — в 9.5) | Хранить тело запроса — дублирование персональных данных |
| W8 | Лимиты | Тело до 32 КБ; на точку — 60 заявок в минуту; в режиме BROWSER дополнительно 10 в минуту с одного IP. Превышение — 429 | — |
| W9 | Модуль и компания отключены | Приём закрыт (404, как для неизвестной точки), сайт продолжает работать — письма приходят как раньше (M5) | Принимать и складывать в очередь — сложнее, не нужно |
| W10 | Подключение сайта Nova | Код сайта **не меняется**: CRM принимает его текущий запрос (заголовок, поля, `submissionId`). В Phase 8: точка приёма Nova с сопоставлением `firstName`+`lastName` → имя, `program` → «Программа» в сообщении, тип `trial`; локальный сквозной тест ровно с тем запросом, который отправляет `api/trial-crm.php`; инструкция и примеры (PHP, Node, браузер) для других сайтов. **Включение на живом сайте** — заполнить две настройки в `api/config.php` на Strato **после развёртывания CRM в интернете** (сейчас CRM только локальная; production — отдельное согласование) | Подключать живой сайт к локальной CRM — невозможно без публичного адреса |

## 5. Изменения схемы

Модели `FormEndpoint` и `FormSubmission` согласованы в Phase 2 (phase2_design.md, раздел 2.2); миграция Phase 8 создаёт их с уточнениями:

- `FormEndpoint`: + `source_detail` (тип заявки), `field_mapping` (переименования и дополнительные поля, JSON), лимиты — константы кода.
- `FormSubmission`: как в Phase 2 (`idempotency_key`, `status`, `error_code`, `lead_id`); уникальность `(tenant_id, endpoint_id, idempotency_key)` — защита от дублей на уровне БД.
- RLS на обеих таблицах (данные компании). Приём запроса: точка ищется по публичному ключу **в контексте компании из hostname** — ключ одной компании на поддомене другой не найдётся.
- Права runtime-роли: `form_endpoints` — SELECT/INSERT/UPDATE; `form_submissions` — SELECT/INSERT (журнал только дополняется).

## 7. Критерии готовности Phase 8

1. Решения W1–W10 согласованы и записаны в SPEC.
2. Администратор компании сам настраивает приём заявок; секреты не видны повторно.
3. Заявка с сайта (SERVER и BROWSER) превращается в лид без дублей; журнал показывает результат без персональных данных.

## 8. Риски

- **Спам через режим BROWSER** — ключ виден всем; защита — разрешённые адреса (только фильтр: вне браузера Origin подделывается), ловушка, лимиты. Точка приёма только создаёт заявки и ничего не возвращает. При реальном спаме — капча отдельным решением.
- **Живой сайт Nova** нельзя подключить до развёртывания CRM (W10). Клиент сайта делает одну попытку без повторов, поэтому заявки, отправленные во время недоступности CRM, придут только письмом — это ожидаемое поведение (письмо остаётся резервным каналом, D6).
- **Инструкция развёртывания сайта Nova.** Пользователь подтвердил (2026-11-17), что форма на живом сайте работает корректно — текущей проблемы нет. Остаётся неточность в `STRATO-DEPLOY.md` сайта: в шаге копирования не упомянут `api/trial-crm.php`, который `trial.php` подключает через `require_once` (в `docs/development/trial-crm.md` он указан). При будущем развёртывании по этой инструкции файл можно забыть — тогда после отправки писем PHP завершится фатальной ошибкой. Стоит дописать файл в инструкцию (репозиторий сайта, вне объёма CRM).
- **Согласие посетителя (GDPR)** — галочка на сайте обязательна, но в отправку не попадает (у поля нет имени, и клиент CRM передаёт только семь полей). Если понадобится хранить факт согласия в CRM — изменить форму на сайте и добавить поле; решение вместе с 9.5.

## 9. Реализация (P8-001, 2026-11-17)

Сделано по W1–W10; подробный отчёт с фактическими проверками — SPEC, «Отчёт по каждому подшагу Phase 8». Инструкция подключения — docs/integrations/web-forms.md.

Код: миграция `20261117100000_phase8_forms`; `apps/api/src/forms/` (`mapping.ts`, `form-endpoints.controller.ts`, `intake.controller.ts`); `apps/api/src/database/forms-store.service.ts`; исключение пути `/api/webhooks/forms/` из проверки Origin в `auth/origin.middleware.ts`; web — раздел `/forms` («Приём заявок»); seed — локальная точка Nova `nova-local-trial-endpoint` с теми же настройками, что нужны живому сайту.

Отличия и уточнения относительно разделов 4–5:

- **W1.** Кроме перечисленных ответов: `403 ORIGIN_NOT_ALLOWED` (режим BROWSER, чужой сайт) и `503 UNAVAILABLE` (внутренняя ошибка; можно повторить с тем же `submissionId`).
- **W3.** Без ключа сайта дублем считается одинаковое содержимое в течение тех же календарных суток UTC (не скользящие 24 часа): ключ — хеш содержимого и даты, его проверяет тот же уникальный индекс.
- **Раздел 5.** Уникальность ключа — частичный индекс только для принятых отправок (`status = 'IMPORTED'`): записи «Дубль» и «Отклонена» с тем же ключом допустимы, а две одновременные одинаковые отправки создают одну заявку. Добавлено ограничение CHECK: секрет есть только у точки SERVER.
- **W7.** Журнал показывает последние 100 записей; очистка старше 90 дней — в 9.5, как и было запланировано.
- **Лимиты (W8)** считаются в той же таблице ограничений PostgreSQL, что и попытки входа; лимит точки проверяется до секрета, поэтому перебор секретов тоже ограничен.
- Удаления точек нет — только отключение (журнал и ссылки на заявки сохраняются).

Подключение живого сайта Nova (W10) не выполнялось: CRM пока только локальная. Порядок — docs/integrations/web-forms.md, раздел 4.
