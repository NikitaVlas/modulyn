# Phase 11 — Выделенная установка у клиента и запуск Nova: план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Прежний план выхода в интернет (одна общая платформа на сервере разработчика): [docs/deployment-plan.md](../docs/deployment-plan.md) — эта фаза его заменяет.
Статус документа: **редакция 1, согласована (2026-11-27)**. Решения E1–E12 и Phase 11 одобрены сообщением «Согласен, начинай». Реализация — раздел 9 и отчёт в SPEC.

## 1. Модель (решение пользователя, 2026-11-27)

Пользователь работает один, клиентов немного, маркетинга нет — это дополнительный заработок, а не массовый SaaS. Поэтому:

- **каждый клиент получает свою установку Modulyn** на своём сервере, со своим доменом и своей почтой;
- **клиент сам оплачивает** сервер, домен и прочие услуги; данные клиента хранятся у клиента;
- **разработчик** (пользователь) готовит нужные клиенту модули локально, выпускает версию и обслуживает установку по договору;
- первый клиент — **Nova**: согласна оплачивать сервер; адрес CRM — **crm.bjjmoenchengladbach.de**.

Подтверждено пользователем: «Nova согласна», «мне самому это выгоднее и удобнее», «все данные будут у них», адрес — «да».

## 2. Цель и границы

Цель: Modulyn можно установить у клиента по инструкции за один рабочий день; Nova работает на crm.bjjmoenchengladbach.de, а заявки с сайта Nova приходят в эту CRM.

Входит: адреса установки на домене клиента, режим одной компании, минимальный брендинг установки, сборка и выпуск версий, файл Compose для сервера, HTTPS, резервные копии в хранилище клиента, наблюдение, инструкции установки, обновления и отката, чек-лист договорённостей с клиентом, запуск Nova (вместе с пользователем — действия на чужих серверах и в чужих аккаунтах выполняет пользователь или по его прямому поручению).

Не входит: оплата и заказ услуг у провайдеров (делает клиент или пользователь); юридический текст договора (только список пунктов); общая многоклиентская платформа (код её поддерживает, но разворачивать её сейчас не нужно); экран настройки брендинга.

## 3. Что есть сейчас (проверено 2026-11-27 по коду)

- Адреса строятся как `<метка>.<APP_BASE_DOMAIN>`: компания — `nova.<домен>`, вход — `app.<домен>`, платформа — `admin.<домен>` (`apps/api/src/tenancy/hostname.ts`, `originFor` в `config/environment.ts`, `apps/web/src/lib/site.ts`). Произвольный адрес вроде `crm.bjjmoenchengladbach.de` для компании задать нельзя.
- Бренд: надпись MODULYN и бирюзовый цвет — около 40 мест в интерфейсе; «Modulyn» в заголовке вкладки и в письмах. Название компании («Nova CRM») уже настраивается.
- Почта — любой SMTP (`COMPOSE_SMTP_URL`, `MAIL_FROM`). Сайт Nova уже отправляет письма через SMTP Strato.
- Образы Docker собираются на той машине, где запускается стек; образ API содержит инструменты сборки (Phase 9, ограничение).
- Резервные копии: `pnpm db:backup` / `db:restore-check` локально в `backups/`.

## 4. Решения для согласования

| ID | Вопрос | Предложение | Альтернативы |
| --- | --- | --- | --- |
| E1 | Модель | **Отдельная установка на клиента**, один общий код. Многокомпанийность в коде остаётся (на установке — одна компания); общую платформу можно развернуть позже без переделок | Удалить многокомпанийность — лишняя работа и потеря варианта на будущее |
| E2 | Адреса установки | Явные адреса в настройке сервера, а не «метка + домен». Для Nova: **CRM — `crm.bjjmoenchengladbach.de`**, вход — `login.crm.bjjmoenchengladbach.de`, платформа (только вы) — `admin.crm.bjjmoenchengladbach.de`. Сотрудники открывают `crm.…`; без входа их на секунду переводит на `login.crm.…` и обратно — как сейчас между поддоменами | Ничего не менять: `nova.crm.…`, `app.crm.…`, `admin.crm.…` (без доработки кода, но адрес CRM длиннее); вход прямо на `crm.…` без отдельного адреса — меняет устройство входа (A5), рискованно |
| E3 | Режим одной компании | Настройка установки «одна компания»: со страницы входа — сразу в CRM (уже так при одной компании), в меню нет «Сменить компанию», адрес входа без компании ведёт в CRM | Оставить как есть — лишний пункт меню и экран выбора из одной компании |
| E4 | Брендинг установки | **Минимальный, настройкой сервера**: название продукта вместо MODULYN (вкладка, шапка, вход, письма), логотип (файл), основной цвет кнопок, имя отправителя писем. Без экрана настройки | Без брендинга сейчас (только название компании); полный брендинг с экраном в CRM — дольше и не нужен при одной компании на установку |
| E5 | Сервер | **VPS клиента в ЕС** (Nova оплачивает): Linux, 2 vCPU, 4 ГБ RAM, от 40 ГБ диска; заказ на аккаунт клиента, ваш SSH-ключ добавляется для обслуживания. Подойдёт VPS у Strato (у Nova там уже домен) или у другого провайдера | Заказывать на себя и перевыставлять счёт — вы становитесь хостером данных клиента, сложнее юридически |
| E6 | Домен и сертификат | Три записи DNS (A) на сервер у регистратора клиента (Strato); бесплатный сертификат Let's Encrypt **на три конкретных имени** с автопродлением — DNS-провайдер с API не нужен | Сертификат на все поддомены (wildcard) — нужен только для общей платформы |
| E7 | Почта CRM | Почтовый ящик на домене клиента (например `crm@bjjmoenchengladbach.de` у Strato) по SMTP — как уже делает сайт Nova; проверка, что письма не попадают в спам (SPF/DKIM домена) | Отдельный почтовый сервис — ещё один аккаунт и счёт |
| E8 | Выпуск версий и обновления | Вы собираете готовые образы Docker с номером версии и кладёте их в **закрытое хранилище образов** (например GitHub Container Registry вашего репозитория); сервер клиента только скачивает нужную версию. Обновление — одна команда; откат — предыдущая версия. Исходный код на сервер клиента не попадает. Заодно — облегчённый образ API (ограничение Phase 9) | Сборка на сервере клиента из git — инструменты сборки и доступ к коду на чужом сервере, обновления медленнее |
| E9 | Резервные копии | Каждую ночь — копия базы, **зашифрованная**, в хранилище клиента вне сервера (например Strato HiDrive или любое S3-совместимое в ЕС); 7 дневных, 4 недельных, 6 месячных; раз в месяц — `db:restore-check`. Ключ шифрования и `PLATFORM_TOTP_KEY` — у вас в менеджере паролей и запечатанной копией у клиента | Копии на том же сервере — пропадут вместе с ним |
| E10 | Наблюдение | Бесплатная внешняя проверка `https://crm.…/api/health/ready` раз в несколько минут с уведомлением вам; предупреждение о заполнении диска | Без наблюдения — о сбое узнаете от клиента |
| E11 | Модули под клиента | Только в общем коде, включаются для компании (как «Заявки»). **Никаких отдельных копий кода под клиента** | Ветка кода на клиента — через полгода несколько разных CRM, каждую обновлять отдельно |
| E12 | Договорённости с клиентом | Чек-лист пунктов договора (без юридического текста): ваш доступ к серверу, окно обновлений, кто отвечает за копии, что получает клиент при уходе (выгрузка данных и копия базы), договор обработки данных (вы — подрядчик с доступом), стоимость установки и ежемесячного обслуживания | Без записанных договорённостей — споры при первом сбое |

## 5. Изменения кода и схемы

- Схема БД не меняется.
- Настройка адресов (E2): `APP_HOST`, `PLATFORM_HOST`, `TENANT_HOSTS` (`crm.bjjmoenchengladbach.de=nova`); при их отсутствии — прежняя схема `<метка>.<APP_BASE_DOMAIN>` (локальная разработка, тесты и общая платформа работают как раньше). Затрагивает разбор Host в API, построение ссылок (письма, переходы) и выбор раздела в Next.js.
- Режим одной компании (E3) и брендинг (E4) — переменные окружения; логотип — файл на сервере; цвет — CSS-переменная вместо фиксированного бирюзового в ~40 местах.
- Файл `docker-compose.prod.yml` (без Mailpit, порты 80/443, сертификаты, автоперезапуск, лимит логов), конфигурация nginx с HTTPS, сборка и публикация образов по версии, скрипт ночной копии с шифрованием и выгрузкой.
- Документы: `docs/install.md` (установка у клиента по шагам), `docs/operations.md` (обновление и откат по версии), чек-лист договорённостей (E12); `docs/deployment-plan.md` помечается устаревшим.

## 7. Критерии готовности

- Nova работает на `https://crm.bjjmoenchengladbach.de`, заявки с сайта приходят в CRM, письма CRM уходят с домена Nova.
- Обновление установки — одной командой по номеру версии; откат — так же.
- Ночные копии зашифрованы, лежат вне сервера и проверены восстановлением.
- Следующего клиента можно установить по `docs/install.md` без изменений кода.

## 8. Риски

- **Обслуживание растёт с числом клиентов.** Каждая установка — обновления, копии, наблюдение. Снижается одной командой обновления (E8) и одинаковой установкой у всех; цена обслуживания — в договоре (E12).
- **Доступ к чужому серверу.** Ваш SSH-ключ на сервере клиента — ответственность; доступ только по ключу, список того, что вы делаете, — в договоре.
- **Почта Strato.** Лимиты отправки и попадание в спам зависят от настроек домена Nova; проверяется пробными письмами в 11.7.
- **Ключи.** Без ключа шифрования копий и `PLATFORM_TOTP_KEY` восстановление неполное (Phase 9); хранение — E9.
- **Немецкие тексты** перед запуском у клиента стоит проверить носителем языка (Phase 10, docs/i18n/review.md).

## 9. Реализация (P11-001, 2026-11-27)

Сделаны 11.2–11.6; 11.7 (запуск Nova) — вместе с пользователем, когда будут сервер, DNS, почта и хранилище. Отчёт с фактическими проверками — SPEC, «Отчёт по каждому подшагу Phase 11».

Код и файлы: `packages/contracts/src/hosting.ts` (адреса установки — общие правила для API и интерфейса); `apps/api/src/config/environment.ts` (адреса, бренд для писем), `tenancy/hostname.ts`; `apps/web/src/lib/site.ts`, `lib/brand.ts`, `components/brand.tsx`, `app/globals.css` (цвет бренда), все экраны (`hosting` вместо `baseDomain`, цвет `brand`); `apps/api/Dockerfile` (образы build / migrate / runtime / backup); `apps/api/scripts/server-env.mjs`, `offsite-backup.mjs`, `backup.mjs` (режим прямого доступа и экспорт); `scripts/release.mjs` (`pnpm release`); `deploy/docker-compose.yml`, `deploy/Caddyfile`; docs/install.md, docs/client-checklist.md, docs/operations.md (раздел 7), docs/deployment-plan.md помечен устаревшим.

Отличия и уточнения относительно раздела 4:

- **E6.** HTTPS — **Caddy** вместо nginx + certbot: сам получает и продлевает сертификаты Let's Encrypt на три имени, сам переводит http → https; заголовок `Server` убран, HSTS без `includeSubDomains`, `X-Forwarded-For` заменяется одним адресом клиента (API доверяет только ему), лимит тела 1 МБ — как у локального nginx.
- **E8.** Четыре образа на версию: `api` (облегчённый: 446 МБ вместо 999 — только production-зависимости, без Prisma CLI, кэшей и инструментов сборки), `migrate` (миграции, команды администратора, генератор `.env`), `web` (без изменений), `backup`.
- **E9.** Копия шифруется **открытым** ключом age на сервере; закрытый ключ только у вас (и запечатанной копией у клиента) — украденный сервер не расшифрует собственные копии. Выгрузка — rclone в любое хранилище клиента, ротация 7/4/6.
- **E10.** Сигнал наблюдения — адрес `BACKUP_PING_URL` (сервисы вида healthchecks.io): успех ночной копии — «жив», ошибка или диск > 85 % — тревога. Проверка доступности `…/api/health/ready` внешним сервисом — в инструкции, настраивается при запуске.
- **E3.** Режим одной компании: нет пункта «Сменить компанию» (переход сразу в компанию после входа уже был). Отдельный адрес входа сохранён (A5 не менялся).
- **E4.** Бренд установки — название, цвет (тёмный и светлый оттенки вычисляются), логотип; в письмах — название и цвет; «Modulyn» убран из текстов интерфейса для клиента (секрет точки приёма, письмо сброса пароля, подсказка «Anfragen-Eingang»).
