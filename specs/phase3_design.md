# Phase 3 — Authentication & RBAC: план и решения

Источник требований, одобрений и статусов: [SPEC](../SPEC.md). Модель данных: [phase2_design.md](phase2_design.md), раздел 2.
Статус документа: **редакция 1, согласована (2026-11-16)**. A2 согласован в изменённом виде («проще — все лиды компании»), A1, A3–A12 — как предложено («остальное одобряю»). Phase 3 одобрена тем же сообщением. Реализация — раздел 8 и отчёт в SPEC.

## 1. Цель и границы

Цель: человек входит один раз (паролем или через Google), видит свои компании, переходит в выбранную и работает только в ней. Backend на каждом запросе проверяет сессию, активность аккаунта, участие именно в этой компании и роль. Platform Admin входит отдельно на `admin.<домен>`, и его вход не даёт доступа к компаниям.

Входит в Phase 3 (подшаги 3.1–3.10 SPEC):

- Миграция auth-таблиц (`user_identities`, `user_sessions`, `login_handoffs`, `tenant_sessions`, `platform_sessions`) и уточнения раздела 4.
- Хеширование паролей, вход по паролю, вход через Google (OIDC), центральный вход и выбор компании, одноразовый переход на поддомен, переключатель компаний.
- Access JWT и refresh-токены в HttpOnly cookies, ротация, обнаружение повторного использования, logout, отзыв.
- Guards: аутентификация, участие в компании из hostname, роль; разделение контекстов tenant / app / platform.
- CSRF/Origin-защита, ограничение частоты входа.
- Вход Platform Admin (пароль) на `admin.<домен>` — только сессия и пустой защищённый раздел. Создание первого администратора — 4.1; в Phase 3 он создаётся seed-скриптом только для локальной среды.
- UI: страницы входа, выбор компании, защищённый каркас с названием компании, переключателем и кнопкой выхода.
- Смена собственного пароля (если согласовано A10).
- Синтетический seed (пароли, Google-идентичность для тестов), unit- и интеграционные тесты, README, SPEC.

Не входит: приглашения, первичная выдача пароля, сброс пароля по email (Phase 5); создание компаний и первого Platform Admin (Phase 4); guard модулей (Phase 6); лиды (Phase 7); production DNS/TLS; 2FA (A11).

## 2. Как это будет работать (простыми словами)

Три «входа» на одном приложении, по hostname:

| Hostname | Кто | Что там |
| --- | --- | --- |
| `app.<домен>` | любой пользователь | форма входа (пароль, «Войти через Google»), список своих компаний |
| `<компания>.<домен>` | участник компании | CRM этой компании |
| `admin.<домен>` | Platform Admin | администрирование платформы |

Сценарий:

1. Пользователь открывает `nova.<домен>`. Сессии нет → редирект на `app.<домен>/login?tenant=nova`. Форма показывает «Вход в Nova CRM» (название берётся из tenants по slug; для неизвестного slug — обычная форма без названия, без раскрытия, существует ли компания).
2. Вход паролем или Google → создаётся **сессия центрального входа** (`user_sessions`, cookie только на `app.<домен>`).
3. Если пришли с `tenant=nova` и участие в Nova активно — сразу переход в Nova; иначе — список компаний (только активные участия в активных компаниях). Если компания одна — переход без списка.
4. **Переход на поддомен** (A6): одноразовый код живёт 60 секунд и привязан к браузеру. `nova.<домен>` обменивает код на **сессию компании** (`tenant_sessions`, cookie только на `nova.<домен>`).
5. Каждый запрос к `nova.<домен>/api/*`: проверка JWT → в одной транзакции компании проверка, что сессия не отозвана, аккаунт активен, участие в Nova активно; роль берётся из БД.
6. Переключатель компаний в меню ведёт на `app.<домен>` (там сессия ещё жива) → выбор → тот же переход.

Почему cookie не общая на `*.<домен>`: общая cookie отправлялась бы в каждую компанию, и ошибка в одной проверке открывала бы все компании. Cookie без `Domain` браузер отправляет только на тот хост, где она создана, поэтому сессия Nova физически не приходит на поддомен Company B.

## 3. Решения для согласования (3.1)

| ID | Вопрос | Предложение | Альтернативы |
| --- | --- | --- | --- |
| A1 | Матрица прав | Раздел 3.1 ниже | — |
| A2 | Какие лиды видит MANAGER | **Согласовано 2026-11-16 («проще — все лиды компании»):** MANAGER видит все лиды своей компании и меняет статус любого из них. Назначает ответственного только TENANT_ADMIN (как в ТЗ). Лиды других компаний по-прежнему недоступны | Отклонены: (a) только назначенные; (b) назначенные + неназначенные с возможностью взять себе |
| A3 | Модель токенов | Access JWT в HttpOnly cookie (10 мин) + случайный refresh-токен (в БД только SHA-256), ротация при каждом обновлении. **Роль не кладётся в JWT** — читается из БД на каждом запросе. JWT содержит `sid`, и сессия проверяется на каждом запросе, поэтому logout и блокировка действуют сразу, а не через 10 минут | Только JWT без проверки в БД — отзыв с задержкой до 10 мин; только непрозрачная сессия без JWT — проще, но ТЗ требует JWT |
| A4 | Сроки жизни | Таблица 3.2 | — |
| A5 | Где вводится пароль | **Только на `app.<домен>`** (и на `admin.<домен>` для платформы). Страница входа показывает название компании, из которой пришёл пользователь, — это и есть «собственная страница авторизации» компании из ТЗ | Отдельная форма на каждом поддомене: сразу сессия компании, но для переключателя пришлось бы входить ещё раз |
| A6 | Защита перехода на поддомен | Переход начинает сам поддомен: `nova/api/auth/handoff/start` ставит cookie `state` на `nova` → `app` выдаёт код, привязанный к `state` → браузер отправляет код POST-формой (не в URL) → `nova` сверяет `state` с cookie (при реализации — через промежуточную пересылку формы на свой хост, раздел 8). Как в OAuth: чужой код нельзя «подсунуть» браузеру жертвы (login CSRF), код не попадает в историю и логи | Код в URL — проще, но остаётся в истории и логах прокси, нет привязки к браузеру |
| A7 | CSRF | Для всех изменяющих запросов (не GET/HEAD/OPTIONS): заголовок `Origin` обязателен и должен совпадать с hostname запроса; тело только `application/json` (форма с чужого сайта так отправить не может без CORS, а CORS выключен). Единственное исключение — приём кода перехода (A6), где разрешён Origin `app.<домен>` и вместо этого проверяется `state`. Cookies: `SameSite=Lax` (access), `SameSite=Strict` (refresh). Поддомены одного домена браузер считает «same-site», поэтому одной SameSite недостаточно — основная защита в проверке Origin | Отдельный CSRF-токен (double submit) — дополнительная сложность без выигрыша при строгой проверке Origin и JSON-only |
| A8 | Пароли | Argon2id (параметры OWASP: память 19 MiB, 2 итерации, параллелизм 1), длина 12–128 символов, без требований «цифра + спецсимвол». Для несуществующего email выполняется проверка с фиктивным хешем, чтобы время ответа не выдавало наличие аккаунта. Сообщение всегда одно: «Неверный email или пароль» (в том числе для заблокированного аккаунта) | Проверка утёкших паролей через внешний сервис HIBP — передача данных наружу, отложено |
| A9 | Ограничение входа | Счётчики в PostgreSQL (без Redis): по IP — 20 попыток за 15 мин, по email — 10 неудачных за 15 мин; превышение → 429 с `Retry-After`. Без постоянной блокировки аккаунта (её мог бы вызвать злоумышленник). Хранится хеш ключа, не email и не IP в открытом виде | Счётчики в памяти процесса — сбрасываются при перезапуске, не работают при нескольких экземплярах API |
| A10 | Смена и сброс пароля | **Смена своего пароля — в Phase 3** (текущий пароль + новый; отзывает все остальные сессии). **Сброс по email — в Phase 5** вместе с приглашениями: обоим нужна отправка писем, а провайдер почты ещё не выбран | Всё в Phase 5 |
| A11 | 2FA для Platform Admin | Не в Phase 3. Предлагается TOTP в Phase 4 до появления реальных компаний, потому что этот аккаунт управляет всеми компаниями | Без 2FA в MVP |
| A12 | Google: кто может войти | Google-вход только для существующего пользователя. Поиск по `sub` в `user_identities`; если привязки нет — по email, только при `email_verified=true`, и тогда привязка создаётся автоматически. Нет пользователя — тот же отказ, что при неверном пароле, без регистрации. Пользователь, у которого есть только Google, пароль не получает. Требуются OAuth-клиент в Google Cloud Console и его client ID/secret в `.env` — **их создаёт пользователь** (инструкция будет в README) | Привязка Google только вручную из профиля после входа паролем — безопаснее, но неудобно для людей без пароля |

### 3.1 Матрица прав (A1)

Реализуются в Phase 3 только guards и роли; сами действия появляются в фазах, указанных в столбце.

| Действие | PLATFORM_ADMIN | TENANT_ADMIN | MANAGER | Фаза |
| --- | --- | --- | --- | --- |
| Войти в CRM компании | нет (нет участия) | да | да | 3 |
| Видеть список своих компаний, переключаться | — | да | да | 3 |
| Сменить свой пароль, выйти, выйти на всех устройствах | да (свой) | да | да | 3 |
| Создавать / отключать компании, включать модули | да | нет | нет | 4, 6 |
| Видеть лиды и пользователей компании | **нет** | да | — | 4.5 |
| Приглашать, менять роли, отключать участие | нет | да (кроме последнего администратора и самого себя) | нет | 5 |
| Видеть лиды компании | нет | все | все (A2) | 7 |
| Менять статус лида | нет | любой | любой (A2) | 7 |
| Назначать ответственного | нет | любого активного участника | нет (A2) | 7 |
| Настраивать приём заявок с сайта | нет | да | нет | 8 |

Ответы при отказе: нет сессии или токен недействителен → 401; сессия есть, но не хватает роли → 403; объект другой компании → 404 (не раскрываем, что объект существует). Неизвестная/отключённая компания по hostname → прежний одинаковый 404 (D9).

### 3.3 Токены и cookies (подробно)

- **JWT:** подпись HS256 отдельным секретом для каждого контекста (`JWT_SECRET_TENANT`, `JWT_SECRET_APP`, `JWT_SECRET_PLATFORM`, ≥ 32 байт, генерирует `env:init`). Claims: `iss=modulyn`, `aud=tenant|app|platform`, `sub` (userId или adminId), `sid` (id сессии), `tid` (tenantId, только tenant), `iat`, `exp`. Проверяются подпись, `aud`, `exp`, а для tenant — `tid` совпадает с компанией из hostname. Разные секреты дают вторую защиту: токен платформы не пройдёт проверку подписи в компании, даже если ошибиться с `aud`.
- **Cookies:** имена `__Host-mdl_at` (access) и `__Host-mdl_rt` (refresh). Префикс `__Host-` браузер принимает только с `Secure`, `Path=/` и без `Domain`, то есть cookie гарантированно не разделяется между поддоменами. Локально по HTTP префикс невозможен, поэтому в development используются имена `mdl_at`/`mdl_rt` без `Secure`; в production выключить `Secure` нельзя (ошибка старта, как с `TRUST_DEV_PROXY_HOST`).
- **Ротация refresh:** `POST /api/auth/refresh` выдаёт новую пару и помечает старую запись `rotated_at`. Если старый токен предъявлен повторно: в пределах 20 с после ротации → 401 «повторите» без отзыва (две вкладки обновились одновременно; браузер уже получил новую cookie); позже → это признак кражи, отзывается вся цепочка (`family_id`) и все сессии компаний, открытые из неё.
- **Проверка на каждом запросе** (tenant): один SQL-запрос в транзакции компании: сессия `sid` существует, не отозвана, не истекла; участие `(tid, sub)` активно; `users.is_active`. Результат — роль для RBAC. Это и делает отзыв мгновенным.
- **Logout** на поддомене отзывает сессию компании и родительскую сессию центрального входа этого браузера вместе со всеми её сессиями компаний (полный выход в этом браузере). «Выйти на всех устройствах» отзывает все сессии пользователя.
- **Автоматический отзыв:** блокировка аккаунта, смена пароля (кроме текущей сессии), отключение участия (только сессии этой компании), отключение компании.

## 4. Изменения схемы относительно phase2_design.md

Миграция Phase 3 создаёт таблицы раздела 2.4 phase2_design.md с уточнениями:

```prisma
model UserSession {
  // ... поля из phase2_design.md
  absoluteExpiresAt DateTime @map("absolute_expires_at") @db.Timestamptz(3) // предел 30 дней для всей цепочки
  tenantSessions    TenantSession[]
}

model TenantSession {
  // ... поля из phase2_design.md
  userSessionId     String   @map("user_session_id") @db.Uuid  // из какой центральной сессии создана (для полного logout)
  absoluteExpiresAt DateTime @map("absolute_expires_at") @db.Timestamptz(3)
  userSession       UserSession @relation(fields: [userSessionId], references: [id], onDelete: Restrict)
  @@index([userSessionId])
}

model PlatformSession {
  // ... поля из phase2_design.md
  absoluteExpiresAt DateTime @map("absolute_expires_at") @db.Timestamptz(3)
}

model LoginHandoff {
  // ... поля из phase2_design.md
  userSessionId String @map("user_session_id") @db.Uuid      // какая центральная сессия выдала код
  stateHash     String @map("state_hash") @db.VarChar(128)   // привязка к браузеру (A6)
}

/// Счётчики ограничения входа (A9). Ключ — хеш (IP или email + назначение), не исходное значение.
model AuthThrottle {
  keyHash     String   @id @map("key_hash") @db.VarChar(128)
  windowStart DateTime @map("window_start") @db.Timestamptz(3)
  count       Int
  @@map("auth_throttle")
}
```

RLS и права:

- `tenant_sessions` — под RLS `tenant_isolation`, как остальные таблицы компаний. Дополнительно политика `tenant_session_self`: в контексте `app.user_id` человек может **отозвать** (UPDATE `revoked_at`) свои сессии во всех компаниях — нужно для logout и «выйти везде» с центрального входа. Читать чужие компании через неё нельзя: политика только на UPDATE, условие `user_id = app.user_id`.
- `user_identities`, `user_sessions`, `login_handoffs`, `platform_sessions`, `auth_throttle` — без RLS (вне компаний); доступ только из модуля auth. ESLint-правило запрещает импорт репозиториев auth из бизнес-модулей.
- `modulyn_app`: SELECT/INSERT/UPDATE на auth-таблицы, DELETE только на `auth_throttle` и `login_handoffs` (очистка просроченных); на `platform_admins` — SELECT и UPDATE (смена пароля).
- Просроченные коды перехода и счётчики удаляются при обращении; отдельный планировщик не нужен.

## 5. Устройство кода (план)

```text
apps/api/src/auth/
  password.service.ts        Argon2id: hash, verify, фиктивная проверка
  tokens.service.ts          JWT подпись/проверка по контексту, генерация refresh, SHA-256
  cookies.ts                 имена и атрибуты cookies по окружению
  sessions.repository.ts     user/tenant/platform sessions, ротация, отзыв цепочки
  throttle.service.ts        A9
  login.controller.ts        app: POST /api/auth/login, /refresh, /logout, GET /me, GET /companies
  handoff.controller.ts      app: POST /api/auth/handoff/issue; tenant: GET /api/auth/handoff/start, POST /api/auth/handoff/complete
  google.controller.ts       app: GET /api/auth/google, GET /api/auth/google/callback
  tenant-auth.controller.ts  tenant: POST /api/auth/refresh, /logout, GET /api/auth/me
  platform-auth.controller.ts platform: POST /api/platform/auth/login, /refresh, /logout, GET /me
  password-change.controller.ts  POST /api/auth/password (A10)
  guards/
    authenticated.guard.ts   проверка JWT нужного контекста + сессии в БД; кладёт principal в контекст запроса
    roles.guard.ts           @Roles('TENANT_ADMIN') и т.п.
    origin.guard.ts          A7 (глобальный)
apps/web/src/
  middleware.ts              по hostname: tenant / app / platform разделы; редирект на вход при отсутствии cookie (только UX)
  app/(app)/login, select-company
  app/(tenant)/ ...          защищённый каркас: шапка с названием компании, переключатель, выход
  app/(platform)/login, ...
```

- Контекст запроса (`request-context.ts`) расширяется: `principal` (userId, sessionId, роль) для tenant, (userId, sessionId) для app, (adminId, sessionId) для platform.
- По умолчанию все маршруты защищены; публичные отмечаются явно `@Public()`. Ошибка в забытом декораторе тогда закрывает доступ, а не открывает.
- Next.js проверяет наличие cookie только для удобства (редирект на вход). Права проверяет только API.
- Тела запросов валидируются схемами; ответы auth никогда не возвращают хеши, токены в JSON или признак существования email.

Зависимости (предложение, версии проверяются при установке): `jose` (JWT), `@node-rs/argon2` (Argon2id с готовыми бинарниками, без компиляции на Windows), `openid-client` (Google OIDC: discovery, PKCE, nonce, проверка ID-токена), `cookie-parser`, `zod` (валидация входных данных).

## 8. Реализация (P3-001, 2026-11-16)

Отличия от плана и решения внутри одобренной фазы:

- **Переход на поддомен — четыре шага вместо трёх.** Ручная проверка в браузере показала: Chrome считает `nova.localhost` и `app.localhost` разными «сайтами» (у `localhost` нет регистрируемого домена), поэтому межсайтовая POST-форма приходит без cookie `state` (SameSite=Lax). Решение: `POST /api/auth/handoff/complete` принимает форму с `app.<домен>` и ничего не проверяет — только отдаёт страницу, которая автоматически отправляет ту же форму на `POST /api/auth/handoff/finish` своего же хоста. Там запрос same-origin, cookie `state` приходит, и выполняются все проверки A6. Код по-прежнему не попадает в URL. В production (`*.modulyn.app` — один сайт) сработал бы и прямой вариант, но решение не зависит от этого.
- **Referrer-Policy страницы выдачи кода — `strict-origin`.** С `no-referrer` (по умолчанию helmet) браузер отправляет межсайтовую форму с `Origin: null`, и проверка Origin её отклоняет. `strict-origin` передаёт только origin, без пути и параметров.
- **`cookie-parser` и `zod` не добавлены.** Разбор заголовка Cookie — 20 строк (`auth/cookies.ts`); входные данные auth — несколько строковых полей с явной проверкой. Добавлены только `jose` 6.2.17, `@node-rs/argon2` 2.2.2, `openid-client` 6.9.0.
- **Доступ к аккаунтам и сессиям — только `src/database/auth-store.service.ts`.** ESLint запрещает его импорт вне `src/auth` (исключение — корень композиции `app.module.ts`).
- **Конфигурация.** Новые переменные: `JWT_SECRET_TENANT|APP|PLATFORM` (обязательны, ≥ 32 символов, разные), `PUBLIC_SCHEME` (`http` разрешён только при `APP_BASE_DOMAIN=localhost`), `PUBLIC_PORT`, `TRUST_PROXY` (Compose), `GOOGLE_CLIENT_ID/SECRET` (необязательны), `GOOGLE_ISSUER` (только для тестов).
- **Синтетические данные.** Seed задаёт локальный пароль `SEED_PASSWORD` всем синтетическим пользователям и создаёт `platform@modulyn.example` (только локально, Phase 4.1 определит настоящий способ). Добавлен `admin@suspended.example` — участник только отключённой компании.
- **Выход на всех устройствах** (`POST /api/auth/logout-all`) добавлен как часть матрицы A1.

## 9. Риски

- **Google OAuth локально.** Google разрешает HTTP-адреса перенаправления только для localhost. Подходит ли `http://app.localhost:8080`, нужно проверить при создании клиента; запасной вариант — отдельный адрес `http://localhost:8080/api/auth/google/callback`, который сразу перенаправляет на `app.localhost`. Production-адрес — `https://app.modulyn.app/...` после согласования DNS/TLS.
- **Одна Next.js-сборка для трёх контекстов.** Разделение по hostname в middleware; ошибка в нём даёт неправильную страницу, но не доступ к данным — данные защищает только API.
- **Проверка сессии в БД на каждом запросе** — один индексированный запрос; это цена мгновенного отзыва.
- **`users` без RLS.** Аккаунты читает только модуль auth; бизнес-модулям импорт запрещён ESLint-правилом. Ответы не раскрывают существование email.
- **Часы и токены.** Допуск расхождения часов при проверке JWT — 30 с.
