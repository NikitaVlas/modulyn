# Modulyn

Модульная multi-tenant CRM. Выполнены Phase 1 (технический каркас), Phase 2 (изоляция компаний: модель данных, миграции, определение компании по поддомену, tenant context, PostgreSQL RLS), Phase 3 (вход по паролю и через Google, выбор и переключение компании, сессии, роли, CSRF, ограничение входа), Phase 4 (администрирование платформы: создание и отключение компаний, второй фактор для администраторов), Phase 5 (сотрудники компании: приглашения по email, роли, отключение доступа, восстановление пароля), Phase 6 (модули компаний: включение платформой, защита API, меню), Phase 7 (заявки: список с фильтрами, карточка, статусы с историей, назначение, ручные заявки) Phase 8 (приём заявок с сайтов любой технологии: точки приёма, защита от дублей, журнал) и Phase 9 (сквозная проверка, матрица защиты всех маршрутов, резервное копирование с проверкой восстановления, сроки хранения и удаление заявки, документация) — **MVP готов к приёмке**: [docs/mvp-acceptance.md](docs/mvp-acceptance.md). После MVP: Phase 10 — интерфейс на трёх языках (немецкий по умолчанию, английский, русский); Phase 11 — **выделенная установка у каждого клиента** (свой сервер, домен и почта клиента; установка — [docs/install.md](docs/install.md)). Эксплуатация: [docs/operations.md](docs/operations.md); план развёртывания: [docs/deployment-plan.md](docs/deployment-plan.md). Планы: [Phase 4](specs/phase4_design.md), [Phase 5](specs/phase5_design.md), [Phase 6](specs/phase6_design.md), [Phase 7](specs/phase7_design.md), [Phase 8](specs/phase8_design.md), [Phase 9](specs/phase9_design.md), [Phase 10](specs/phase10_design.md), [Phase 11](specs/phase11_design.md). Источник плана, разрешений и статусов: [SPEC.md](SPEC.md); модель данных: [specs/phase2_design.md](specs/phase2_design.md); вход и сессии: [specs/phase3_design.md](specs/phase3_design.md).

## Требования

- Node.js 26.13.0 (версия закреплена в `.node-version`).
- pnpm 12.21.0 (поле `packageManager`). Если установлен другой pnpm, используйте `npx --yes pnpm@12.21.0` вместо `pnpm` во всех командах ниже.
- Docker Engine и Compose; Docker Desktop должен быть запущен на Windows.
- Свободные локальные порты: 8080 (Compose), 5433 (PostgreSQL), 3000 и 3001 (разработка без контейнеров приложений).
- Доступ в интернет при `pnpm install`: Prisma скачивает свой schema engine (нужен для миграций).

## Быстрый запуск в Docker

Из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm env:init
pnpm stack:up
pnpm db:seed
pnpm smoke
```

`env:init` создаёт `.env` со случайными паролями и не печатает их. Если `.env` уже есть (например, после Phase 1), скрипт только дописывает недостающие переменные. Единственное изменение существующего значения: `DATABASE_URL` со старым суперпользователем переводится на runtime-роль `modulyn_app`, а старое подключение сохраняется как `DATABASE_ADMIN_URL`. `.env` исключён из Git и Docker build context; `.env.example` описывает все переменные.

`stack:up` запускает db → migrate → api, web → proxy. Одноразовый сервис `migrate` создаёт роли БД и применяет миграции; API стартует только после его успешного завершения и подключается как `modulyn_app`. `db:seed` создаёт синтетические компании для проверки — только для локальной среды.

Открыть:

- http://nova.localhost:8080 — CRM компании Nova: без сессии перенаправляет на вход `app.localhost` с заголовком «Вход в Nova CRM».
- http://app.localhost:8080 — центральный вход и выбор компании.
- http://admin.localhost:8080 — вход администратора платформы.
- http://nova.localhost:8080/api/tenant — компания текущего поддомена: `{"slug":"nova","displayName":"Nova CRM"}`.
- http://company-b.localhost:8080/api/tenant — другая компания на том же приложении.
- http://suspended-co.localhost:8080/api/tenant и http://unknown.localhost:8080/api/tenant — одинаковый 404.
- http://nova.localhost:8080/api/health и `/api/health/ready` — liveness и readiness.

Если система не разрешает `*.localhost`, добавьте в hosts `127.0.0.1 nova.localhost company-b.localhost admin.localhost`. Smoke передаёт hostname в заголовке Host, подключаясь к 127.0.0.1, поэтому от DNS не зависит. `SMOKE_ORIGIN` позволяет выбрать другой локальный адрес и порт.

```sh
docker compose ps -a
docker compose logs --tail=100 migrate api web proxy db
pnpm stack:down
```

`stack:down` сохраняет named volume PostgreSQL. Не используйте `docker compose down -v`, если данные нужно сохранить. Изменение `POSTGRES_PASSWORD` в `.env` не меняет пароль уже созданной БД; пароли ролей `modulyn_owner` и `modulyn_app` обновляются автоматически при каждом запуске `migrate` или `pnpm db:roles`.

## Вход и сессии (Phase 3)

Синтетические учётные записи из `pnpm db:seed` (только локально; пароль у всех — `SEED_PASSWORD` в [apps/api/scripts/seed.mjs](apps/api/scripts/seed.mjs)):

| Email | Где | Роль |
| --- | --- | --- |
| `manager@shared.example` | Nova и Company B | менеджер в обеих — для проверки переключения |
| `admin@nova.example` | Nova | администратор компании |
| `admin@company-b.example` | Company B | администратор компании |
| `admin@suspended.example` | только отключённая компания | список компаний пуст |
| `platform@modulyn.example` | `admin.localhost` | администратор платформы (при первом входе — настройка второго фактора) |

Как устроено:

- Пароль вводится только на `app.<домен>` (и `admin.<домен>` для платформы). После входа — список компаний; переход в компанию — одноразовым кодом (60 с), привязанным к браузеру, без кода в URL.
- Cookies `HttpOnly`, без `Domain`: сессия Nova не отправляется на Company B. С https — префикс `__Host-` и `Secure`.
- Access JWT (10 мин, платформа — 5) подписан отдельным ключом для каждого контекста; сессия проверяется в БД на каждом запросе, поэтому выход, блокировка, отключение участия и смена пароля действуют сразу. Refresh-токен меняется при каждом обновлении; повтор старого токена отзывает всю цепочку.
- Изменяющие запросы принимаются только с `Origin` своего хоста и `Content-Type: application/json`. Вход ограничен: 20 попыток с IP и 10 неудачных на аккаунт за 15 минут (HTTP 429).

### Вход через Google

Без настройки кнопка Google скрыта. Чтобы включить:

1. Google Cloud Console → APIs & Services → Credentials → Create credentials → OAuth client ID → тип **Web application**.
2. Authorized redirect URI: `http://app.localhost:8080/api/auth/google/callback` (для `pnpm dev` — порт 3000). Если Google не примет адрес `app.localhost`, сообщите — предусмотрен запасной вариант (specs/phase3_design.md, раздел «Риски»).
3. Записать Client ID и Client secret в `.env` как `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET`, затем `pnpm stack:up`.

Войти через Google может только существующий пользователь: Google-аккаунт привязывается при первом входе, если email подтверждён Google и совпадает с email аккаунта. Регистрации нет.

## Администрирование платформы (Phase 4)

Первого и последующих администраторов платформы создаёт только команда на сервере — публичной регистрации и встроенного пароля нет:

```sh
pnpm platform:admin create --email you@example.com --name "Ваше имя"
```

Команда один раз печатает временный пароль (действует 7 дней). Вход на http://admin.localhost:8080: временный пароль → свой постоянный пароль → обязательная настройка второго фактора (QR-код для приложения-аутентификатора и 10 одноразовых кодов восстановления). Дальше каждый вход — пароль и 6-значный код.

Другие команды: `reset-password` (новый временный пароль), `reset-2fa` (потерян телефон и коды), `block` / `unblock` — все с `--email`. В Docker: `docker compose run --rm migrate node apps/api/scripts/platform-admin.mjs create --email … --name …`.

В разделе «Компании»:

- **Новая компания** — название, имя в интерфейсе, поддомен (после создания не меняется), email и имя первого администратора компании. Ему уходит приглашение по email (Phase 5); участником он становится, когда примет его.
- **Карточка компании** — изменить названия, отключить (поддомен сразу закрыт, все сеансы завершены, данные сохраняются) или включить.
- Администратор платформы видит только настройки компаний и число участников — без заявок, имён и email сотрудников. Все действия записываются в журнал аудита платформы.

`PLATFORM_TOTP_KEY` в `.env` шифрует секреты второго фактора. Не теряйте его: без него всем администраторам платформы придётся заново настроить второй фактор (`reset-2fa`).

## Сотрудники компании и почта (Phase 5)

- **Пригласить сотрудника:** администратор компании → «Пользователи» → email, имя, роль. Человек получает письмо со ссылкой (7 дней, одноразовая): новый задаёт имя и пароль (или «Принять через Google» с тем же email), существующий входит своим аккаунтом и нажимает «Принять».
- **Роли и доступ:** там же — сменить роль, отключить или включить сотрудника (отключение сразу закрывает доступ к этой компании, другие компании человека не затрагиваются). Себя изменить нельзя; последнего администратора — тоже.
- **Новая компания:** платформа отправляет приглашение её первому администратору; в карточке компании можно пригласить ещё раз или пригласить другого администратора.
- **Забыли пароль?** — ссылка на странице входа; письмо со ссылкой на 1 час.

Письма локально не уходят наружу: их перехватывает **Mailpit** — http://localhost:8025 (запускается вместе со стеком и `pnpm infra:up`).

Для production задайте почтовый сервис в `.env`: `COMPOSE_SMTP_URL=smtps://user:pass@smtp.example.com:465` (или `smtp://…:587`) и `MAIL_FROM="Modulyn <no-reply@ваш-домен>"`. У почтового сервиса настройте для домена отправителя SPF, DKIM и DMARC — иначе письма попадут в спам.

## Модули (Phase 6)

У каждой компании свой набор разделов. Модули включает и отключает администратор платформы: `admin.<домен>` → «Компании» → карточка компании → «Модули». Сейчас модуль один — «Заявки»; у новых компаний он включён сразу.

Отключённый модуль пропадает из меню CRM компании, а сервер отвечает на его запросы `403 MODULE_DISABLED` — для любой роли. Данные модуля сохраняются и возвращаются при повторном включении.

Новый модуль добавляет разработчик: код в общей кодовой базе, запись в `apps/api/src/modules/registry.ts`, миграция каталога и `@RequireModule('<ключ>')` на контроллере модуля.

## Заявки (Phase 7)

Раздел «Заявки» (если модуль включён у компании):

- **Список** — имя, контакт, источник, статус, ответственный, дата; фильтры по статусам и ответственному («Мои», «Без ответственного», сотрудник), поиск по имени, email или телефону, сортировка по дате, по 25 на странице. Фильтры хранятся в адресе — ссылку можно отправить коллеге.
- **Карточка** — данные, сообщение из формы, история статусов (когда, кто, с какого на какой). Сменить статус может любой сотрудник (любой статус → любой); если заявку только что изменил коллега, появится «Заявку уже изменили» и карточка обновится. Ответственного назначает только администратор компании.
- **Новая заявка** — для звонка или визита: имя и email или телефон.

Менеджер видит все заявки своей компании. Заявки других компаний недоступны ни в списке, ни по ссылке. Удаления и редактирования заявок пока нет: ненужные заявки закрываются статусом «Закрыта».

## Приём заявок с сайтов (Phase 8)

Сайт компании на любой технологии отправляет заявку одним запросом `POST https://<компания>.<домен>/api/webhooks/forms/<ключ>` с JSON — заявка появляется в «Заявках» со статусом «Новая» и источником «Форма сайта». Инструкция для разработчика сайта, ответы API и примеры (PHP, Node.js, браузер): [docs/integrations/web-forms.md](docs/integrations/web-forms.md).

- **Настройка:** администратор компании → «Приём заявок» (виден при включённом модуле «Заявки»). Режим «С сервера сайта» — секрет показывается один раз, в БД хранится хеш, «Новый секрет» сразу отменяет старый. Режим «Из браузера» — для статических сайтов: только с указанных адресов сайта, ловушка для ботов, 10 заявок в минуту с одного посетителя.
- **Дубли:** повтор с тем же `submissionId` (или `Idempotency-Key`) не создаёт вторую заявку.
- **Журнал:** время, точка, результат и причина отказа — без содержимого форм.
- **Отключение** точки, модуля или компании закрывает приём (404).

Локально `pnpm db:seed` создаёт в Nova точку `nova-local-trial-endpoint`, настроенную как для сайта Nova (секрет — `SEED_INTAKE` в [apps/api/scripts/seed.mjs](apps/api/scripts/seed.mjs)); `pnpm smoke` отправляет на неё заявку в формате сайта Nova. Живой сайт Nova подключается после развёртывания CRM в интернете — раздел 4 инструкции.

## Языки (Phase 10)

Интерфейс, сообщения сервера и письма — на **немецком (по умолчанию)**, английском или русском.

- **Переключатель DE · EN · RU** — на страницах входа, приглашения и восстановления пароля и в шапке CRM и платформы. После входа выбор сохраняется в аккаунте: тот же язык на всех устройствах и во всех компаниях человека. До входа — в cookie `modulyn_lang` этого браузера. Язык браузера не угадывается: кто ничего не выбирал, видит немецкий.
- **Письма:** приглашение — на языке того, кто приглашает (страница приглашения открывается на нём же, новый аккаунт получает язык, на котором человек принял приглашение); восстановление пароля — на языке аккаунта.
- **Данные не переводятся:** имена, тексты заявок, названия компаний и подписи полей, введённые администратором (например, «Programm» у точки приёма), остаются как введены.
- **Переводы** — в `packages/i18n/src/messages/`: каждая фраза сразу на трёх языках; пропущенный язык — ошибка сборки, разные подстановки в языках — ошибка unit-теста. Таблица всех фраз для проверки носителем языка: [docs/i18n/review.md](docs/i18n/review.md) (пересобрать: `node packages/i18n/scripts/review-table.mjs` после `pnpm --filter @modulyn/i18n build`). Новый язык — новое поле в каждой фразе и значение в `LOCALES`.
## Установка у клиента (Phase 11)

Каждый клиент получает свою установку: сервер, домен и почта клиента, данные — у клиента. Код один; на сервер попадают только готовые образы нужной версии.

- **Выпуск версии:** `MODULYN_REGISTRY=ghcr.io/<логин> pnpm release 0.11.0 --push` — образы `modulyn-api` (облегчённый), `modulyn-migrate` (миграции и команды администратора), `modulyn-web`, `modulyn-backup` (ночные копии); без `--push` — только локально.
- **Сервер клиента:** `deploy/docker-compose.yml` и `deploy/Caddyfile` (HTTPS с автоматическим сертификатом), `.env` из генератора `server-env.mjs`. Пошагово — [docs/install.md](docs/install.md); обновление, откат и проверка копий — [docs/operations.md](docs/operations.md), раздел 7; договорённости с клиентом — [docs/client-checklist.md](docs/client-checklist.md).
- **Адреса:** явные адреса установки — `APP_HOST` (вход), `PLATFORM_HOST` (платформа), `TENANT_HOSTS` (`crm.<домен>=<компания>`); одна компания — без пункта «Сменить компанию». Без этих переменных — прежняя схема `<метка>.<APP_BASE_DOMAIN>` (локальная разработка).
- **Бренд:** `BRAND_NAME`, `BRAND_COLOR` (#RRGGBB), `BRAND_LOGO_URL` — название вместо MODULYN, цвет кнопок, логотип, имя в письмах; без настройки — Modulyn.

## Разработка с перезагрузкой

```sh
pnpm env:init
pnpm infra:up
pnpm db:setup
pnpm db:seed
pnpm dev
```

`pnpm dev` загружает `.env`, собирает contracts и API (включая `prisma generate`), запускает TypeScript watch, перезапуск API и Next.js dev. Открыть http://nova.localhost:3000; Next.js перенаправляет `/api/*` на API :3001. Next.js при этом подменяет Host, поэтому только в этом режиме API принимает исходный hostname из `X-Forwarded-Host` от loopback (`TRUST_DEV_PROXY_HOST`, в production запрещён).

## База данных

| Команда | Что делает | Под какой ролью |
| --- | --- | --- |
| `pnpm db:roles` | создаёт/обновляет роли `modulyn_owner` и `modulyn_app` | суперпользователь (`DATABASE_ADMIN_URL`) |
| `pnpm db:migrate` | `prisma migrate deploy` | владелец схемы (`MIGRATION_DATABASE_URL`) |
| `pnpm db:setup` | roles + migrate | — |
| `pnpm db:seed` | синтетические nova, company-b, suspended-co; отказывается при `NODE_ENV=production` | владелец схемы |
| `pnpm db:drift` | сравнивает живую БД со `schema.prisma`; пустой diff — код 0 | владелец схемы |
| `pnpm db:backup` | резервная копия в `backups/` (+ сводка для проверки) | суперпользователь, `pg_dump` в контейнере `db` |
| `pnpm db:restore-check <файл>` | восстанавливает копию в отдельную базу и сверяет; рабочая база не меняется | суперпользователь |
| `pnpm db:cleanup` | удаляет устаревшие технические записи по срокам хранения (API делает это раз в час) | `modulyn_app` (только вызов функции) |

Копии, восстановление после аварии, ключи, сроки хранения, диагностика — [docs/operations.md](docs/operations.md).

API работает только под `modulyn_app`. Если `DATABASE_URL` указывает на суперпользователя, роль с BYPASSRLS или владельца таблиц, readiness и все операции с данными компаний отвечают 503, а в логе указывается причина. Prisma не отслеживает CHECK-ограничения, RLS-политики и GRANT: они в SQL миграций (`apps/api/prisma/migrations`). Новые миграции создаются командой `prisma migrate dev` в `apps/api`; RLS для новых таблиц с `tenant_id` дописывается в их SQL вручную по образцу `20261116130000_phase2_rls`.

`pnpm check` выполняет typecheck, lint, unit-тесты и build без базы данных. `pnpm test:integration` требует запущенный PostgreSQL (`pnpm infra:up`): пересоздаёт отдельную базу `<POSTGRES_DB>_test`, создаёт роли, применяет миграции и seed, затем проверяет изоляцию компаний под ролью `modulyn_app` (чтение, изменение, удаление, IDOR, RLS без контекста, пул соединений, конкурентные запросы, менеджер в двух компаниях) и вход (пароль, переход в компанию, ротация и отзыв сессий, границы tenant/app/platform, CSRF, ограничение входа, Google через локальный поддельный OIDC-провайдер), а также (Phase 9) сквозной сценарий от новой компании до обработанной заявки с сайта (`e2e.test.mjs`), матрицу всех маршрутов API — без входа, с чужой компанией, с ролью ниже, при отключённом модуле, с чужим Origin (`security-matrix.test.mjs`; новый маршрут без защиты или новый публичный маршрут уронит тест), очистку и удаление заявки (`retention.test.mjs`). Рабочая база не затрагивается. Smoke требует запущенный стек и `pnpm db:seed`.

- `/api/health` → 200, `{ "status": "ok", "service": "modulyn-api" }` на любом hostname.
- `/api/health/ready` → 200, `{ "status": "ready", "database": "up" }`; 503 при недоступной БД или небезопасной роли.
- `/api/tenant` → 200 с `slug` и `displayName` для активной компании; 404 одинакового вида для неизвестной, отключённой, зарезервированной (`www`, `api`, …), вложенной или чужой.

1. `packages/config/tsconfig.base.json` — общие строгие правила TypeScript.
2. `packages/contracts/src/index.ts` — публичные типы ответов API, без моделей БД.

5. `apps/api/scripts/db-roles.mjs` — роли БД; `scripts/seed.mjs` — синтетические данные.
6. `apps/api/src/tenancy/hostname.ts` — разбор Host в компанию; `tenancy.middleware.ts` — поиск компании и контекст запроса; `request-context.ts` — AsyncLocalStorage.

8. `apps/api/test/integration/isolation.test.mjs` — доказательства изоляции.
9. Вход (Phase 3): `apps/api/src/auth/auth.guard.ts` — глобальная проверка каждого запроса; `sessions.service.ts` — выдача, проверка и ротация сессий; `auth.controller.ts` — маршруты входа и перехода в компанию; `origin.middleware.ts` — CSRF; `src/database/auth-store.service.ts` — единственный доступ к аккаунтам и сессиям; `apps/web/src/features/auth` — страницы входа, выбора компании и каркас CRM. ## Ограничения

MVP проверен локально; в интернете не развёрнут (план — [docs/deployment-plan.md](docs/deployment-plan.md)). Нет редактирования заявок (удаление — только администратором, по запросу); нет удаления точек приёма (только отключение) и CAPTCHA для форм «из браузера»; сайт Nova к CRM ещё не подключён (нужно развёртывание в интернете). Письма в production требуют настроенного почтового сервиса (SMTP, SPF/DKIM/DMARC). Вход через настоящий Google проверяется после создания OAuth-клиента (автотесты используют поддельного провайдера). Production TLS/DNS не настроены. Runtime-образ API содержит build dependencies и Prisma CLI (нужен сервису migrate).
