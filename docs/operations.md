# Эксплуатация Modulyn

Для того, кто запускает и обслуживает систему. Запуск с нуля — [README](../README.md); план выхода в интернет — [deployment-plan.md](deployment-plan.md). Все команды — из корня проекта (если установлен другой pnpm: `npx --yes pnpm@12.21.0 <команда>`).

## 1. Из чего состоит система

| Сервис (Docker Compose) | Что делает | Данные |
|---|---|---|
| `proxy` (nginx) | Единственный вход снаружи: `*.домен` → web или API (`/api/*`) | нет |
| `web` (Next.js) | Интерфейс: вход, CRM компании, администрирование платформы | нет |
| `api` (NestJS) | Вся логика и проверка прав; раз в час — очистка устаревших записей | нет |
| `migrate` | Одноразово перед API: роли БД и миграции | нет |
| `db` (PostgreSQL 18) | Все данные; изоляция компаний — RLS | volume `postgres_data` |
| `mailpit` | **Только локально**: перехватывает письма (http://localhost:8025) | нет |

Компания определяется по поддомену: `nova.<домен>` — CRM компании Nova, `app.<домен>` — общий вход и выбор компании, `admin.<домен>` — администрирование платформы.

## 2. Переменные окружения (`.env`)

`pnpm env:init` создаёт `.env` со случайными паролями и ключами и ничего не печатает. `.env` не попадает в git и в Docker-образы.

| Переменная | Назначение | Если потерять или изменить |
|---|---|---|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT` | Суперпользователь и имя базы (контейнер `db`) | Пароль уже созданной базы не меняется сменой переменной |
| `DATABASE_ADMIN_URL` | Подключение суперпользователя: роли, тесты, резервные копии | — |
| `DB_OWNER_PASSWORD`, `MIGRATION_DATABASE_URL` | Владелец схемы: миграции, seed, команды платформы | Обновляется при каждом `migrate` |
| `DB_APP_PASSWORD`, `DATABASE_URL` | Роль API `modulyn_app` (без обхода RLS) | Обновляется при каждом `migrate` |
| `JWT_SECRET_TENANT`, `JWT_SECRET_APP`, `JWT_SECRET_PLATFORM` | Подпись токенов доступа, по ключу на контекст | Все пользователи войдут заново; данные целы |
| `PLATFORM_TOTP_KEY` | Шифрует секреты второго фактора администраторов платформы | **Без него** всем администраторам платформы нужен `pnpm platform:admin reset-2fa` |
| `APP_BASE_DOMAIN`, `PUBLIC_SCHEME`, `PUBLIC_PORT`, `HTTP_PORT` | Домен и публичный адрес (`http` разрешён только для `localhost`) | Неверные — не работают ссылки в письмах и переходы между поддоменами |
| `SMTP_URL`, `COMPOSE_SMTP_URL`, `MAIL_FROM` | Почта: приглашения, сброс пароля | Письма не уходят (приглашение можно отправить повторно) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Вход через Google (необязательно) | Кнопка Google скрыта |
| `NODE_ENV`, `API_PORT` | Режим и порт API | — |

## 3. Резервные копии и восстановление

### Сделать копию

```sh
pnpm db:backup
```

Создаёт `backups/modulyn-<дата>-<время>.dump` (формат `pg_dump` custom) и рядом `.json` — сводку для проверки: число строк в каждой таблице, миграции, RLS, права. Сводка без данных. Папка `backups/` не попадает в git и в Docker-образы. Файлы копии содержат персональные данные — храните их так же бережно, как базу.

### Проверить, что копия восстанавливается

```sh
pnpm db:restore-check backups/modulyn-<дата>-<время>.dump
```

Восстанавливает копию в **отдельную** базу `<POSTGRES_DB>_restore_check` (рабочая не затрагивается), сверяет со сводкой число строк по таблицам, миграции, RLS-политики, права роли API и проверяет, что роль API без контекста компании не видит заявок. Затем удаляет проверочную базу (`--keep` — оставить для осмотра). Ответ `OK` или `FAILED` со списком расхождений. Проверяйте каждую новую схему копирования и хотя бы раз в месяц.

### Восстановить рабочую базу из копии (авария)

Восстановление заменяет текущие данные: всё, что появилось после копии, пропадёт. Перед началом сделайте копию текущего состояния, даже повреждённого.

```sh
pnpm db:backup                                     # копия текущего состояния
docker compose stop api web                        # никто не пишет в базу
docker compose exec -T db dropdb -U modulyn --if-exists modulyn
docker compose exec -T db createdb -U modulyn modulyn
docker compose exec -T db pg_restore -U modulyn -d modulyn --exit-on-error < backups/<файл>.dump
pnpm stack:up                                      # migrate обновит роли и применит новые миграции
pnpm smoke                                         # только локально (synthetic seed)
```

Имя пользователя и базы — значения `POSTGRES_USER` и `POSTGRES_DB`. На новом сервере сначала `pnpm env:init`, затем перенесите из старого `.env` ключи (раздел 3.1), затем восстановление.

### 3.1. Что хранить вместе с копией

Копия базы без ключей восстанавливается, но:

- без `PLATFORM_TOTP_KEY` администраторам платформы придётся заново настроить второй фактор;
- без `JWT_SECRET_*` все войдут заново (это не страшно).

Храните `PLATFORM_TOTP_KEY` (и при желании весь `.env`) **отдельно от копий** — в менеджере паролей или сейфе, не рядом с файлами `.dump`.

## 4. Сроки хранения и очистка

API раз в час вызывает функцию базы `modulyn_cleanup()`; вручную — `pnpm db:cleanup` (печатает, сколько записей удалено).

| Что | Сколько хранится |
|---|---|
| Коды перехода, ссылки сброса пароля, счётчики ограничения попыток | 1 день после окончания |
| Сессии (вход, компании, платформа) | 30 дней после окончания или выхода |
| Приглашения | 30 дней после принятия, отзыва или истечения |
| Журнал приёма заявок с сайтов | 90 дней |
| Журналы аудита компании и платформы | 1 год |
| **Заявки и их история** | **Не удаляются автоматически** — пока компания их хранит |

Сроки заданы в миграции `20261117120000_phase9_retention` (функция `modulyn_cleanup`); изменить срок — новая миграция с новой версией функции. Это предложение для MVP; для реальных данных срок хранения заявок подтверждает компания (владелец данных).

**Удаление заявки по запросу человека** (право на удаление данных): администратор компании → карточка заявки → «Удалить заявку». Заявка и её история удаляются безвозвратно, в журнале приёма ссылка обнуляется, в аудите остаётся только факт удаления без имени и контактов. Вернуть можно только из резервной копии — учтите это: копии старше даты удаления ещё содержат данные человека и исчезают по мере их ротации.

## 5. Диагностика

| Признак | Что проверить |
|---|---|
| Страница не открывается | `docker compose ps -a` — все сервисы `healthy`, `migrate` — `exited (0)` |
| «Сервис временно недоступен» в интерфейсе | `docker compose logs --tail=100 api` — API не запущен или не подключается к базе |
| `/api/health/ready` → 503 | База недоступна или `DATABASE_URL` не на роли `modulyn_app` (в логе API — причина) |
| После обновления 502 | `docker compose up -d --wait`; nginx находит новые контейнеры сам (resolver Docker) |
| Не приходят письма | Локально — http://localhost:8025; иначе `COMPOSE_SMTP_URL`, `MAIL_FROM`, лог API «Mail delivery failed: <код>» |
| Сайт не может отправить заявку | «Приём заявок» → журнал (причина: неверный секрет, чужой сайт, данные); точка и модуль включены; адрес — поддомен этой компании |
| Компания «пропала» | Отключена платформой (поддомен отвечает 404): `admin.<домен>` → «Компании» → «Включить» |
| Модуль пропал из меню | Отключён платформой у этой компании (данные сохранены) |
| `pnpm db:drift` нашёл расхождения | Кто-то менял схему вручную; сравните с `apps/api/prisma/migrations` |

Логи API не содержат паролей, токенов, данных форм и email из заявок — только коды ошибок и числа.

## 6. Обычные операции

| Задача | Как |
|---|---|
| Первый администратор платформы | `pnpm platform:admin create --email … --name …` (временный пароль печатается один раз) |
| Потерян телефон администратора платформы | `pnpm platform:admin reset-2fa --email …` |
| Новая компания | `admin.<домен>` → «Компании» → «Новая компания» (приглашение уходит первому администратору) |
| Сотрудники | Администратор компании → «Пользователи» |
| Подключить сайт | Администратор компании → «Приём заявок»; инструкция для сайта — [integrations/web-forms.md](integrations/web-forms.md) |
| Обновить версию | `git pull`, `pnpm install --frozen-lockfile`, `pnpm db:backup`, `pnpm stack:up` (миграции применяются автоматически), `pnpm smoke` (локально) |
